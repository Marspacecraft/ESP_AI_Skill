# ESP AI Skill 设计与文档总览

> **本文是入口：整体是什么、怎么分层、核心机制有哪些、其余细节在哪个文件。**
> 它不复制细节——细节只有一处，复制就会漂移，而漂移是静默的。
> 约定过的决定在各文档自己的「决定记录」章节里（局部编号，跨文件不复用）。还没做到的事，在对应文件的缺口章节或同名 `.txt` 里。

---

## 1. 这是什么

一个跑在 **ESP32 全系**（FreeRTOS 一族）上的 **App 开发框架**，外加一个 host 伪平台用于跑测试。

**名字只有一个**：项目叫 **ESP AI Skill**。**MarsAIReader 是它的一个默认硬件平台**——一块 ESP32 墨水屏阅读器，用来把"写 App"和"接一块板"两条路径都走通一遍；它不是框架的名字，也不是唯一形态（换板、换一个不一定是阅读器的 App，框架不改）。

意思是：**让 AI agent（或人）只写 `apps/` 下的业务 App，就能在 ESP32 上跑起来**；框架、接口、门禁、平台适配由各自的角色维护，用机器判定保证写出来的 App 不会跨层、不会停不下来。

- **"AI" 指的是开发方式，不是运行时能力。** 固件本身不做模型推理、不做动态加载、不内置 LLM。
- **本仓库做框架、应用层公共逻辑，也做平台适配**：`platform/host-fake/` 是参考实现，每块真实板子是 `platform/` 下的一个子目录。
- **框架只提供机制、不拥有任务**；平台层由各硬件平台自行实现，缺的能力返回 `CM_ERR_NOT_SUPPORTED`。

**两个对外用途，都是一等用途，不是一主一辅**：写 App（tag 2）、把一块板接进来（tag 4）。只有 App 侧顺、平台侧得先读懂框架源码，这套东西就退化成"只有原作者能移植"。

## 2. 三层

```
apps/       应用层    一个 App = 描述体 + init/exit/task 三个回调 + 一条主任务
   │                  系统 App（管理器、各能力服务）tag 1 ／ 业务 App tag 2
   ▼
framework/  框架层    只有机制：生命周期、注册表、事件、伪阻塞。无 task/timer/队列实例
   │
   ▼
platform/   平台层    只实现 pf_ops_t 九项 + .version，以及 pf_rtos 那张原语表。每块板一个目录，共用 tag 4
```

`api/` 是**唯一**的横向通道，按"谁看得见"拆两支：`af_api/`（App）、`fp_api/`（框架↔平台，暂不使用）。类型与错误码**不在 `api/` 里**，在仓库根的 `common/`（全层可读）——放 `api/` 任何一支都会造成反向依赖。

依赖方向只有一条：`apps → framework → platform`。唯一的反向例外是事件从下往上走（`fw_event_post`）。

**机制细节**见 [architecture.md](architecture.md)；目录与 include 规则见 [code-structure.md](code-structure.md)。

## 3. 四条核心机制

这四条是整套设计的承重点，其余都是它们的推论。

| 机制 | 一句话 | 为什么关键 |
|---|---|---|
| **伪阻塞** | 会阻塞的接口内部检查取消位，命中就调 `exit()` 且**不返回** | 于是"`fw_delay_block()` 之后的代码可能永远不执行"是正常路径：App 不需要检查返回值、不需要写状态机，清理只有一处（`exit()`） |
| **提交型接口** | `disp_commit` 之类调用即返回、同 key 覆盖、最终一致 | AI 结构上做不到"刷坏屏"，不是靠约定而是靠没给接口 |
| **服务注册表** | 未注册→`CM_ERR_NOT_SUPPORTED`，宿主 `FAILED`→`CM_ERR_UNAVAILABLE`，返回前查取消位 | 伪阻塞的保证落在**一处**；同时区分"没这能力"与"有但坏了" |
| **机器判定** | 依赖 / 符号 / 写入三道判定 + `policy.txt` | 让"不跨层、不停不下来"从"作者自觉"变成"过不了就红" |

四条的不变量、失败模式、以及"AI 拿不到 `fp_api/`"这类编译期隔离，见 [architecture.md](architecture.md) §3 与 [access-control.md](access-control.md) §4。

## 4. 谁写什么

**tag 是架构分层，不是人。** 一个人可以持多个 tag；同一层也可以有多个人。

| 层 | tag | 角色 | 典型任务 |
|---|---|---|---|
| 应用层 · 系统 App | 1 `sysapp` | A | 管理器、能力服务宿主 |
| 应用层 · 业务 App | 2 `aiapp` | B | 写业务 App（对外的主路径；默认形态是阅读器） |
| 框架层 | 3 `framework` | B | 生命周期、注册表、事件 |
| 平台层 | 4 `platform` | C | 把一块板接进来（共用同一个 tag） |
| 接口层 | 5 `api` | D | 定义 `api/`、搭骨架、写门禁与文档 |

**完整权限矩阵、每个角色的停止条件、加 App / 加板 / 加 tag 的流程**见 [roles.md](roles.md)。
**谁能读/写哪个目录、机器凭什么判**见 [access-control.md](access-control.md)。

## 5. 两条路径的闭环

这套框架有两条对外路径，各自有自己的闭环定义。

| 路径 | 做到什么算完 |
|---|---|
| **App 侧** | `apps/demo/` + 生命周期测试六条在 host 上跑出数字（见 [app-model.md](app-model.md) §7） |
| **平台侧** | `platform/<板>/` + `tests/port/` 一致性套件在 host 上跑绿：九项语义用同一份套件自证 |

平台侧缺了一致性套件，"我这块板对不对"就只能烧进去试——而九项硬必需的错误恰恰都是**烧进去也看不出来**的那种（相对超时写成绝对截止 → 跑两天偶发卡死；`sleep_ms` 忙等 → 只是功耗高）。

## 7. 文档纪律

1. **结论必须落到文档才算定案。** 只出现在对话里的结论视为"未定"，不得据此写代码。
2. **落文档时同时写"为什么"。** 只写"决定用注册表"而不写"因为伪阻塞的保证必须落在一处"，下一个人会把这个决定重新讨论一遍。
3. **一个事实只有一处。** 决定→各文档的「决定记录」，术语→[glossary.md](glossary.md)，权限→[roles.md](roles.md) + `policy.txt`（冲突时以 `policy.txt` 为准），还没做到的事→对应文件的缺口章节或同名 `.txt`。别处只链接。
4. **每份文档有「决定记录」，只追加不删除。** 被推翻的移到同名 `.txt` 或该文档的缺口章节，编号不复用——否则会被人重新提出。
5. **文档与代码同 PR。** 改了行为不改文档，视同没改。
6. **每份文档开头写清"它回答什么问题"。** 两份文档回答同一个问题，就会出现两套事实。
7. **接口的权威定义是头文件，不是文档。** 文档只写约束、理由、失败模式，不复制函数签名——复制就会漂移，而漂移是静默的。
8. **`docs/generated/` 是生成物**，不手改，由 `tools/gen_catalog.py` 生成。
9. **定稿＝冻结，要改需评审。** 定稿文件不得随意修改，改动必须走同一条路：**提理由 + 给 diff 提案 → 评审批准 → 才落盘 → 升版本号**。没有"小改不用审"的例外——这几份文件的失效方式都是静默的（权限只错一行、契约只差一句，都没有症状）。
   - 标记写法：`.md` 在标题下一行加 `> **状态：定稿 vX.Y（YYYY-MM-DD）**`；`.txt`/无 md 配对的用文件头横幅（见 `policy.txt` 顶部）。
   - 未定稿的不标；**不要提前标定稿**，否则等于宣布一份还在讨论的文档是契约。
   - 定稿清单不单独维护：看每份 `.md` 顶部的状态行即可，别处不重复列。
10. **定稿时删除同名 `.txt`。** `.txt` 只服务评审期，内容是"还没定、还没做、有歧义"的事项；文档定稿意味着这些问题**已经裁决完毕**，此时留着 txt 会变成第二份事实来源（下一个人照着 txt 里已解决的问题再问一遍）。
   - 顺序：先把 txt 里每条**裁决结果**写进 md（或写进该文档的「决定记录」）→ 再删 txt → 再标定稿。
   - 待办不跟着删：txt 里若有**还没落地的门禁、没实现的判定、待办的检查**，先把它们迁到能承载"待办"的那份 txt（目前是 `code-structure.txt`，门禁类事项的落点），再删本文件。`access-control.txt` 就是这么处理掉的。
   - 例外：没有 md 配对的清单类文件不适用这条（本仓库目前没有这种文件）。
   - **AI 没有删除权限**（沙箱禁止 `rm`），删文件由人执行；AI 只能把待删文件内容清空并写一行"已并入 X，本文件待删除"。

## 8. 版本约定

- 标题带版本：v0.1 草案 → v0.2 结构成型 → v1.0 可据以实现。
- 只改措辞不动结构：不升版本。
- 改分层、改决策、改契约：升次版本号，并在该文档的「决定记录」里留一行。
- **`定稿`（规则 9）不绑版本号**：任何版本都可以标，标了就是**冻结**——此后改动一律按规则 9 走（提理由 + diff → 批准 → 落盘 + 升次版本号）。v0.x 不标，因为还没到"可据以实现"。
  - 这条原写"只在 v1.0 标"，与现状不符：`access-control.md` 是 **定稿 v1.2**、`architecture.md` 是 **定稿 v1.2**、`coding-style.md` 是 **定稿 v1.3**——它们都是标了定稿之后又按规则升的版本。冻结与版本号无关，跟"改过几次"才是两回事。
- **版本号是文档版本，不代表任何东西被实现了。** 实现状态看代码本身与各文件的同名 `.txt`。
