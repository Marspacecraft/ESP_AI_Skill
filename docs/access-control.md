# 代码访问权限 v1.2

> **状态：定稿 v1.2（2026-10-30）**

> 本文只写设计结果。还没有落地的工作项在 [code-structure.txt](code-structure.txt)（`check_policy.py` 还要查的两件事）。

**这份文档回答什么问题**：谁（哪一类代码）可以读哪个目录、可以写哪个目录；这个约定凭什么能被机器判定，而不是靠自觉。

数据的唯一来源是仓库根目录的 `policy.txt`（定稿 v1.4）。本文只写语义、理由和失败模式，**不复制那张表**——表在 `policy.txt` 里，抄一份到这里就会漂移。

---

## 1. 模型

两个维度：**角色**（谁）与**路径**（哪里）。

**tag 是架构分层，不是人。** 一个人可以同时持多个 tag，同一层也可以有多个人。
把 tag 当成"用户名"，在第三块板、第二个 AI 出现时就会撞。

| tag | 名字 | 是哪一层 | 写什么 |
|---|---|---|---|
| 1 | `sysapp` | 应用层 | 系统 App：管理器（id 1）+ 各服务 App |
| 2 | `aiapp` | 应用层 | AI / 业务 App（`apps/demo/`） |
| 3 | `framework` | 框架层 | 机制、生命周期、注册表、事件 |
| 4 | `platform` | 平台层 | 平台契约的实现。**虚拟平台与所有真实板共用这一个 tag** |
| 5 | `api` | 接口层 | `api/`、`common/`、平台公共接口、门禁、文档 —— 只定义，不实现业务 |

> **tag 4 不按板拆分。** 首版曾把每块板各给一个 tag，结果是"第二块新板无处安放"。
> 现在所有平台实现共用一个 tag 4，靠目录前缀区分是哪块板；隔离性变弱
> （持 tag 4 的人能改所有板），换来"加一块板只加一行前缀"。这个交换是刻意的：
> 平台适配是一等用途，加板的成本必须低。

每个 tag 声明两样东西：

- **写权限**：`role` 行的前缀，说明"这个 tag 的代码住在哪个目录"。一个文件的角色集合 = 匹配它的最长 `role` 前缀（可能不止一条，见 §2.4）。
- **读权限**：由 `read` 行按路径前缀授予。它与写权限是两条**独立**的线：`read` 行管不着写，`role` 行管不着能不能 include。

写入权限是白名单：**没写进去的路径，谁都不能写**。因此不需要一条条写"禁止"——AI 不能写 `framework/`，不是因为它被禁止，而是因为没有任何 `role` 行覆盖那里。

只有人能写的（刻意留白）：全部构建文件与 CI（`CMakeLists.txt`、`partitions.csv`、`sdkconfig.defaults`、`.github/`）、`policy.txt` 自己、以及仓库根的 `AGENTS.md`（入口文件，AI 改入口等于改自己的行为准则）。这些都是**不写进任何 `role` 行**，靠"未列出 = 无人可写"生效，**不是靠一句禁令**——没有写进 `policy.txt` 的"禁止"都只是口号。

## 2. 四条语义（缺一条就有歧义）

### 2.1 `r` 的含义：允许 include 它的头，不是禁止阅读源码

同一份 checkout、同一个文件系统，**没有任何工具能阻止一个 agent 去读一个文件**。所以：

- `r` = 这个角色的代码可以 `#include` 该路径下的头文件。
- **能链接一个符号 = 能 include 声明它的那个头。** 链接权不跟实现文件走：`fw_app_state_of()` 的实现在 `framework/src/` 里，tag 1 不需要"能读 `framework/src/`"也能调用它——只要它能 include 声明它的 `framework/include/fw_app.h`。
- `.c` 的读权只影响"能不能看、能不能改源码"，不影响链接。所以 `read framework/` 只给 3 和 5，而 `read framework/include/` 给 1、3、5。
- `r` ≠ 保密。想要真正的保密只能物理隔离（子模块、独立仓库、不同权限的 CI runner）。

把 `r` 当成保密边界，会在第一次 code review 时发现它不成立，然后整套约定被当成"形式主义"丢掉。

### 2.2 最长前缀优先；命中同样长度时并集放行

一个路径会同时命中多行（`apps/` 与 `apps/system/`）。规则是**取最长的匹配**：

- tag 2 读 `apps/app_manifest.h` → 命中 `apps/app_manifest.h`（比 `apps/` 长）→ 允许
- tag 2 读 `apps/system/manager/manager.h` → 命中 `apps/system/` → 拒绝

写权限用同一套规则，并且**允许"同样长度"命中多条时全部生效**：

- `role 1` 与 `role 2` 都写了 `apps/app_manifest.c`（同一前缀、长度相同）→ 两个 tag 都能写。

这不是"按行序取第一个"。判定结果与遍历顺序无关，就不会有"有时拦、有时不拦"那种最难查的 bug。

反过来说，一条路径下的角色必须能被这两条规则**完全确定**：要么长度不同（短的那个被长的截断），要么长度相同（并集）。**"长度不同却都想生效"是不允许的**——那就是歧义。

### 2.3 未列出的路径 = 无人可读写

`policy.txt` 里没出现的路径，默认拒绝。这条必须显式写进规格：默认允许的话，新增一个目录就等于默认对所有角色开放，而这个"开放"不会出现在任何 diff 里。

"前缀覆盖到哪儿"同样重要，而且两个方向都有坑：

- **`platform/` 的整棵在 `role 5` 里**，所以 `platform/` 下任何新子目录（包括一块还没加进 `role 4` 的新板）都落在 tag 5 名下。这是刻意的：`platform/` 的公共部分必须有人维护，宁可让"加板漏写前缀"靠 review 拦住，也不留"无人可写"的死洞。
- **仓库根目录下新出现的顶层目录不属于任何人。** `role 5` 只列了具名目录，没有 catch-all。新建顶层目录必须先由人在 `policy.txt` 加一行，否则它谁也写不了。

### 2.4 一个文件可以有多个角色

旧版写"`writes` 前缀之间不得重叠到同一个文件"，理由是重叠会让"这个文件的角色"不唯一、判定取决于遍历顺序。那个结论太强了。精确的说法是两条：

1. **重叠但长度不同 = 正常**。`role 1 apps/` 与 `role 2 apps/demo/` 同时存在时，"谁拥有 `apps/demo/x.c`" 有唯一答案（最长的那个），不是歧义。
2. **重叠且长度相同 = 允许多个角色，并集放行**。目前唯一的例子是 `apps/app_manifest.c` / `.h`：注册清单只有一份，系统 App 与 AI 的 App 都得往末尾追加自己的条目。

所以判定的完整表述是：**一个文件的角色集合 = 匹配它的最长前缀（可能多条）**。它比"一个文件一个角色"更准确，也解释了清单为什么能共写。

顺带一条推论：`tests/` 与 `docs/` 必须按 **tag** 分（`tests/sys/` 与 `docs/sys/` 归 1、`tests/app/` 与 `docs/app/` 归 2、`tests/framework/` 与 `docs/framework/` 归 3、`tests/platform/` 与 `docs/platform/` 归 4，其余归 5），不能写成"按开发角色分"——角色不是 tag，一个角色可能同时持 1、3、4，而一个目录上的写权只能按 tag 表达。

## 3. 权限表

表在 `policy.txt`（定稿 v1.4）。这里只写"为什么是这几条"，不复制数据。

- **`api/` 分两支，而 `common/` 在 `api/` 外面。**
  - `api/af_api/`：App 面向，1 2 3 5 可读。**AI 拿不到 `api/fp_api/`**——机制面不在它的可链接集合里，"伪阻塞由框架一处保证"才是真的，而不是"每个作者各自记得做"。
  - `api/fp_api/`：框架↔平台，3 4 5 可读。
  - `api/` 的根只给 5 写。两支的边界是"这一层能不能看见"，不是保密。
  - 类型与错误码不在 `api/` 里，在 `common/include/`（`cm_types.h`、`cm_err.h`），全层可读：它们要跨层共享，放 `api/` 的任何一支都会造成反向依赖。
- **`framework/` 写权只在 3，`framework/include/` 给 1、3、5 读。**
  系统 App 必须能 include 控制面（`fw_app_state_of()`、`fw_app_stop()`），否则管理器拉不起别人；**漏了这条会表现为链接期 undefined symbol，而不是权限报错**。给 5 读是因为生命周期测试要直接驱动框架，不是让 5 去改实现（写权在 3）。**tag 2 一处都不给。**
- **`platform/`**：各板目录归 4 写、公共部分归 5 写，读权 3 4 5；`platform/host-fake/` 额外给 3 读，因为框架测试要链接它的 `g_pf_ops`。板子之间靠目录前缀区分，不再各占一个 tag。
- **`apps/` 是混合区。** `apps/demo/`（2 写）、`apps/system/`（1 写）、`apps/` 根（5 写、1 2 5 读，用来放应用层共享接口头）。**AI 新建 App 必须在 `apps/demo/` 下。**
- **唯一的例外是 `apps/app_manifest.c` / `.h`**：写权 1+2，读权 1 2 3（框架侧要读清单做合并、查重 id）。它落在 `apps/` 之下却由两个 tag 共写，靠的是 §2.2 的"同长并集"。
- **`tests/` 与 `docs/` 按 tag 分**（见 §2.4 末尾），其余归 5。
- **`tools/` 与 `skills/` 的最终归属只有人**——AI 能改 skill 就能删掉约束，然后证明自己合规。`skills/` 已在 `policy.txt` v1.5 收回（不再归 `role 5`）；`tools/` 仍由 `role 5` 代管，收回条件是门禁稳定（见 `policy.txt` 末尾「待收紧」）。

## 4. 三条判定

三条都是集合包含，无运行时开销。**三条都需要身份**（`--as <tag|human>`）：可读集合、可写区、写入白名单全都按 tag 查表，脚本不会猜。**三个都判**——不因为"另外两条看着与该次改动无关"就跳过；跳过等于给出一条"只判一条"的旁路。

未声明身份时，三条一律不跑，并且明说这不是通过：

```
SKIP 未声明身份（--as <tag|human>）。
三条判定都没有运行 —— 这不是通过。
```

两条配套规则，缺一条都会让 `SKIP` 变成后门：

- **本地**：不计为违规（否则每次本地跑全量门禁都会被自己的身份缺失卡住）。
- **CI**：**未声明身份直接判红**（返回非 0）。否则"不写 `--as`"就成了"跳过全部判定且退出码为 0"的合法路径——那条路只要存在，整套判定就是可选的。判据用 CI 环境变量（`CI` 非空）区分，不新增参数。

### 4.1 读权：用编译器的真实解析结果，不自己解析 include

对每个源文件跑一次预处理器，取它实际展开到的**每一个头的绝对路径**：

```
clang -std=c11 -M -I<该 tag 允许的 include 路径> -c apps/demo/x/app.c
```

输出里的每个依赖路径都必须落在该 tag 可读的集合里（按 §2.2 判）。

**为什么不用正则扫 `#include` 行**：正则只能看字面量，而 C 的 include 解析是编译器行为——`../` 相对路径、`-I` 搜索顺序、`#include_next`、`__has_include`，每一条都能绕过字面匹配。用 `-M` 拿到的是编译器自己的答案，无处可绕。

### 4.2 符号：两问，按顺序问

编译完成后，取两样东西：

```
clang -std=c11 -I<允许的路径> -c apps/demo/x/app.c -o app.o
llvm-nm --undefined-only -g app.o     # 这个单元用到了、但没在自己这里定义的符号
```

判据**不是**"符号定义在哪个目录"，而是：

1. **这个符号的定义是不是也在可写区域？** 是 → 这是你自己的代码（自己的全局变量、自己的 helper），放行，不再往下问。
2. **否则**它必须在一个**调用者不可写**的头里被声明，且那个头必须是该编译单元实际 include 过的（4.1 那一步已经拿到了真实依赖列表，在这些头的文本里查标识符即可）。落在可写前缀下的头，只在这一步"不算数"。

**为什么是两问而不是一问。** 旧判据只要求"符号出现在某个实际 include 过的头里"，于是可以绕：

```c
/* apps/demo/x/x.h —— tag 2 自己可写 */
void fw_run_exit(void);             /* 一行声明 */

/* apps/demo/x/app.c */
#include "x.h"                      /* 实际 include 过 */
... fw_run_exit();                  /* 旧判据：通过 */
```

`apps/demo/x/x.h` 在 tag 2 的可写区里，所以它能自己造一份"权威声明"。补上第 2 问的"不可写"之后这条路断了。

但第 1 问不能省。少了它，"AI 在自己的头里声明自己 App 的描述体、再由清单 include"这个**正当**写法会被误判——因为那两者都在 tag 2 的可写区里。判据拦的是"引用别人的东西"，不是"引用自己的东西"。

实现上，第 1 问需要一份"可写区定义了哪些全局符号"的集合：对可写路径下的 `.c` 各自 `clang -c` 后 `nm --defined-only` 汇总即可，不需要链接整个固件。

四条推论：

- `api/` 里声明、`framework/` 里实现的函数**顺利通过**——定义不在可写区，但声明就在 App include 的 `api/` 头里。按"定义位置"判会把所有正常调用都当违规，那样门禁没法用。
- `extern void fw_run_exit(void);` 直接写在 `app.c` 里**被拦住**——定义在 framework（不在可写区），声明又不出现在任何被 include 的头里。
- 写在**自己可写的头**里再 include，**也被拦住**（上面那段）——`fw_run_exit` 的定义不在可写区，第 1 问不成立，第 2 问里那个头又不作数。这一条不补，前面所有"AI 拿不到机制面"的论述都是纸上的。
- 仓库里找不到定义的符号（`memcpy`、`snprintf`）是外部依赖，不判。

**为什么必须有这一条**：不 include 任何头，直接一行 `extern` 声明就能调用任意符号。C 没有访问控制，include 白名单对它完全无效。而任何形式的越权最终都要落到符号表上——`extern`、函数指针、宏拼接、改名 include 都一样。这一条把"权限"从文本约定变成链接事实。

### 4.3 写入：路径前缀

`git diff --name-only` 的每个路径，所属角色集合里必须至少有一个对该路径有写权（§2.4）。CI 与本地同一条规则。

配套一条针对注册清单的细则：**对 `apps/app_manifest.c` 只能追加**（不得删除或修改既有行，决定 10）。否则可以把自己的 App 写成 `APP_FLAG_SYSTEM`，或把别人的条目删掉。判定实现是"diff 只增 + 新增行必须引用 `apps/demo/` 下的对象"。

两个 tag 共写同一个文件还有一个代价：**冲突面比单写者大**。加 App 之前先拉一次代码，别等写完才发现清单被别人改过。

## 5. 为什么值得做

- **AI 是主要开发者**：靠文档说"不要碰 framework"是一次性约定；下一次会话它就不记得了。写成策略表 + 三条判定，才是每次都会被检查的。
- **失败是静默的**：绕过框架直接调器件，代码能编译、能跑、甚至看起来正常，直到换板时才发现这一层根本没起作用。这类问题在运行时不报错，只能在构建期拦。
- **成本低**：整张表是数据，判定是集合查找；三条检查跑完是秒级。

## 6. 常见任务要改哪些文件

| 任务 | 改 | 不改 |
|---|---|---|
| AI 加一个 App | `apps/demo/<app>/` + `apps/app_manifest.c` 末尾追加一行 | 其它一切 |
| 加一个系统 App | `apps/system/` + 清单追加一行（tag 1 也有写权） | `api/`（除非要暴露新能力） |
| 新增一个能力（如 `stor`） | `api/af_api/stor.h` + 实现（`framework/src/` 或服务 App）+ 能力目录登记 + `policy.txt` 里补需要的 `read` 行 | 各平台目录。**v1 不新增能力头**：屏幕（`disp`）是单独立项、不在 v1，别拿它当模板 |
| 移植一块新板 | 人先在 `policy.txt` 的 `role 4` 行尾加 `platform/<板>/`；然后 tag 4 写实现 | `framework/`、`api/` |

最后一行是需要留意的代价：**加平台要动 `policy.txt`**。这是刻意的——新平台意味着新的写入区域，这应该出现在 diff 里。顺序也不能反：先加前缀再建目录，否则目录会先落在接口层名下（§2.3）。

| 10 | 注册清单能否整体重写 | **已定：只能追加，不能重写。** 清单被 tag 1 与 tag 2 共写（决定 16），允许整份重写等于任一方都能改坏对方的条目：把别人的条目删掉，或把自己的 App 改写成 `APP_FLAG_SYSTEM` 绕过管理器的启动策略。判定见 §4.3（diff 只增 + 新增行只引用自己目录下的对象） |
| 12 | 无身份时怎么处置 | **已定：三个都判，没有身份就三个都不跑**，`SKIP` 且本地不计违规；**CI 里未声明身份直接判红**（返回非 0）。否则"不写 `--as`"就是一条"跳过全部判定且退出码为 0"的合法路径 |
| 13 | 判定器要不要能改代码 | **已定：只读**。三条判定只报告，不自动修——自动修会让人失去"越权正在发生"的感知 |
| 14 | 符号来源的头必须不可写 | **已定：两问**——①符号的定义在可写区 → 放行；②否则必须在一个调用者不可写的头里声明。理由见 §4.2 的反例。**第 1 问不能省** |
| 15 | 链接权跟什么算 | **已定：跟声明，不跟实现**——能链接一个符号 = 能 include 声明它的头。否则 tag 1 为了调一个控制面函数就得能读整个 `framework/`，机制面隔离退化成"只是不能改" |
| 16 | 一个文件能否有多个角色 | **已定：能，条件是"同样长度的前缀"**，命中多条则并集放行。首例是 `apps/app_manifest.c` / `.h`（tag 1 与 2 共写，tag 3 读）。旧版"一个文件只属于一个角色"太强，会把共写清单判成歧义 |

### 7.1 为什么系统 App 用目录而不是清单

清单方案的理由是"目录可以被挪文件绕过"。这条理由在**写入**上不成立：写入本来就由 §4.3 按路径前缀判定，而路径前缀天然知道 `apps/system/`。也就是说，目录方案不是"没有清单就没人管"，而是**把清单换成了路径前缀**，而路径前缀恰好是写入判定本来就要用的东西。

- 收益：少一份要与目录同步的数据；`apps/` 的结构一眼能看出谁是谁。
- 代价：必须显式禁止 tag 2 写 `apps/system/**`——白名单天然做到（`role 2` 的前缀里没有它）。

## 8. 为什么数据格式是行格式而不是 TOML/JSON

- **TOML**：本机 python 是 `3.11.0a3`，没有 `tomllib`（它要 3.11 正式版），而 `pip install tomli` 在这个环境装不上（网络受限）。用一个本地无法解析的格式描述策略，等于让策略表无法自校验。
- **JSON**：`json` 是标准库，但放不下注释——而这个文件的注释承载着"为什么"，删掉就会被人重新讨论一遍。
- **行格式**：零依赖、`diff` 友好、与仓库里已有的 `tools/purity_rules.txt` 同一种写法。代价是不能嵌套——但权限表本来就只是两张平面表。
