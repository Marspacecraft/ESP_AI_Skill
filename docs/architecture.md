# ESP AI Skill 架构设计（v1.2）

> **状态：定稿 v1.2（2026-10-30）**
>
> 改动要走评审：提理由 + diff → 批准 → 落盘 → 升版本号。
>
> **定位：面向 ESP32 全系（FreeRTOS 一族）的 App 开发框架 / 开发套件，外加一个 host 伪平台用于跑测试。**
>
> **名字只有一个，别混**：项目叫 **ESP AI Skill**（这套框架）。**MarsAIReader 是它的一个默认硬件平台**——一块 ESP32 上的墨水屏阅读器，用来把"App + 平台"两条路径都走通一遍；它不是框架的名字，也不是唯一形态。换一块板、换一个不一定是阅读器的 App，框架一行不改。
>
> 不是"与硬件无关"。真实取舍是：**框架层与本仓库内的公共代码不碰任何 SDK**（这是纯度边界，由 `tools/check_purity.py` 强制，理由见 §2.2）；**平台层允许直接用 ESP-IDF / FreeRTOS**，把芯片、总线、面板、RTOS 差异全部吸收在 `platform/` 里，不向上渗透。
>
> 多平台抽象只覆盖两条**真实存在**的目标：**ESP32 全系**、**host-fake**。不为假想中的第三族 RTOS 预先付代价——真的要接非 FreeRTOS 的板子时再抽（见 §11.2 T5）。
>
> 本仓库的范围：**框架层** + **应用层公共逻辑** + **平台层契约** + **平台适配工具链** + **skill 与门禁**。
> 平台适配**也是这套框架的一等用途**：`platform/host-fake/` 是参考实现，每块真实板子是 `platform/` 下的一个子目录（**没有脚手架目录**——新板从空目录开始，按契约自主写；`policy.txt` 里所有平台实现共用 tag 4，靠目录前缀区分是哪块板；加一块板只加一行前缀，不新增 tag）。一份 `pf_ops_t` 写得对不对，由 `tests/port/` 的一致性套件在 host 上先判一半——**没有这条回路，"平台适配"就只能靠真机试错**。引脚、总线、上电时序、面板传输、器件驱动全在 `platform/<板>/` 里，契约以 `platform/port/pf_ops.h` 与 `pf_rtos.h` 两个头为准。
>
> 本文 §1–§10 是设计结果，**§11 是缺口与待议**（还没做的、还没定的）。

> **语言边界**：本仓库内的 `common/` `api/` `framework/` 一律是**标准 C11**，不 include 芯片 SDK、RTOS、图形库，也不出现它们的标识符（产品仓库的 `apps/` 允许 **C++17**，但同样不许 include 平台专有头）。编译器差异只收敛在 `common/include/cm_port.h`；这条规则由 `tools/check_purity.py` 强制。框架要任务/信号量时不碰 RTOS，走 `platform/port/pf_rtos.h`（见 [code-structure.md](code-structure.md) §2.2）。平台差异由平台包在 `platform/` 里吸收，不向上渗透。

> **术语约定（贯穿全部文档）**：
>
> - **"0 号"** 是对**管理器 App** 的历史叫法，它的 `app_id_t` **是 1**。`0` 恒为无效哨兵——不要找 id 为 0 的 App，也不要以为有两个"管理器"。
> - **回调名是 `exit`**，不是 `on_exit`。`init` / `exit` / `task` 三个成员就这三个名字。
> - **`svc_id_t` 与 `app_id_t` 是两个不同的域**。服务 id 不能拿去查 App 状态表，要先用 `fw_svc_owner(svc_id)` 换成 `app_id_t`。
> - **平台目录是 `platform/<板>/`**（`host-fake/`、`metalio_eink_4_plus/`、`otherplatform/`），不是 `platform/boards/<板>/`，以 `policy.txt` 为准。其中 **`metalio_eink_4_plus/` 就是 MarsAIReader 的目录**（见 [glossary.md](glossary.md)「名字」）。

## 0. 分层与解耦

```
common/              人人可用的基础设施（类型、原子、链表、错误码、TLS）
api/                 应用层契约面：公共头 + 能力目录（无实现）
framework/           框架层：不能运行的代码（无 task / 无 timer / 无硬件句柄）
platform/port/       平台层接口要求：pf_ops_t（九项，NULL 表示不支持）+ pf_rtos.h（RTOS 原语表）
skills/              给 AI 的工作流与硬约束
tests/               host 单测（含 host-fake 平台）

apps/                本仓库只放最小可写集（见下）
  demo/              AI 的样板 App：可编译、可被生命周期测试驱动
  app_manifest.c     AI 业务 App 的清单（tag 1 与 tag 2 共写，只许在末尾追加一行）
                     ← 系统 App 的清单在 `apps/system/system_manifest.c`，按作者分多份（§1.4）
  system/            系统 App：引导、生命周期、监控、配额、能力汇总；服务宿主（display/input/audio/net）
                     ← 属产品仓库，不在本仓库
```

**`apps/` 与"产品仓库"的边界**：本仓库是**开发套件**，所以必须自带一套能跑的最小 App 集——否则 `policy.txt` 里给 tag 2 写的三条路径（`apps/demo/`、`apps/app_manifest.c`、`apps/app_manifest.h`）指向不存在的目录，AI 无处落笔，v1 验收线里的"生命周期测试"也没有驱动对象。

### 0.1 解耦规则

| 规则                     | 说明                                                                  |
| ------------------------ | --------------------------------------------------------------------- |
| 只能调**相邻下一层**     | `apps → framework → platform`；app 不得直接调 `pf_*`                  |
| 不允许跨层               | app 不得 include `platform/`；platform 不得 include `apps/` 与 `api/` |
| 同层可调                 | app 调 app 允许，但**经 `api/` 转发、不直接链接对方符号**（"服务"的形态） |
| framework 不持有运行权   | 无 task、无 timer、无队列实例；机制绑定在宿主 App 上执行              |
| framework 不 push 给 app | 只提供 wait/peek，App 自己 pend —— 这就是"框架不能调用应用"           |
| **platform 只实现 port** | 平台包不认识任何 App，只知道 `pf_ops_t` 与能力位                    |

### 0.2 唯一例外：事件从下往上走

若严格要求"只能向下调用"，平台的中断 / DMA 完成回调将**无法产生事件**。因此开一条白名单：

```c
/* platform → framework 允许调用的全部函数，仅这两个 */
void fw_event_post(evt_topic_t topic, const void *payload, size_t n);   /* 任务上下文 */
void fw_event_post_isr(evt_topic_t topic, const void *payload);         /* ISR 上下文 */
```

- 只能调这两个；不得调 framework 其它函数，**不得调任何 app**。
- framework 仍然不调 app：事件只是入队，App 自己 `fw_event_wait()` 取。
- 这条白名单可用 include / 符号图静态检查。

## 1. App 的定义

App = **一个模块 + 一个主任务 + 一份 manifest**。它不是进程，没有地址空间隔离；价值是**可被调度、可被停止、可被计量**。

```c
typedef struct app_desc {
    app_id_t    id;                            /* 2..254 由 AI 分配；0 = 无效哨兵，1 固化给管理器 */
    const char *name;                          /* 给人看的名字：日志、UI */
    cm_err_t (*init)(app_ctx_t *ctx);          /* 建资源 */
    void     (*exit)(app_ctx_t *ctx);          /* 所有结束路径都调用恰好一次；文档正文统一叫 exit() */
    void     (*task)(app_ctx_t *ctx);          /* 主任务体，必须可协作退出 */
    uint32_t    flags;                         /* APP_FLAG_SYSTEM */
} app_desc_t;
```

> 权威定义是 `api/af_api/app.h`；完整契约（伪阻塞、退出顺序）见
> [app-model.md](app-model.md)。本节只保留架构层面的形态。

### 1.1 主任务的强制形态

```c
for (;;) {
    do_work();
    fw_delay_block(100);   /* 伪阻塞：被取消时不返回这里，直接走退出路径 */
}
```

没有 `fw_event_wait(...) == OK` 这种写法。**App 不检查返回值、不写状态机、不轮询取消位**——
一旦写了，就等于把"停得下来"这件事从框架的保证降级成作者的自律。

### 1.2 停止协议（为什么不能强杀）

`vTaskDelete` 一个卡在 `while(1)` 里、还**持着互斥锁**的任务 → 锁永远不还 → 整机从"某 App 卡住"恶化为"全系统死锁"。

1. 管理器置状态 `STOPPING` 并置取消位（**不投递"停止消息"**，App 不需要处理它）；
2. 任务在下一个伪阻塞点发现取消位 → 清零取消位（= 在 exit 期间禁用取消）→ 调 `exit()` → 框架回收托管资源 → 置终态 → 结束任务（完整七步见 §3.1.1）；
3. **超时未退** → 只观测并报告（管理器不打日志刷屏，只在状态变化时打一行）；自动重启属管理器策略，不在本仓库；
4. 极端情况只能重启整机。

> **能力上限要写进 skill**：这是"有界退化"，不是沙箱，AI 不能假设有内存隔离。

### 1.3 状态机

```
EMPTY ──start──> INIT ──init成功──> RUNNING ──request_stop──> STOPPING ──> STOPPED
                   │                    │
               init失败             task 正常返回（自愿退出）
                   └──────> FAILED      └──────────────────────────────> STOPPED

STOPPED ──start──> INIT        （可重启：取消位在收尾时已清零）
```

只有 6 个状态，**没有"暂停"**——单 MCU 上暂停等于"占着资源不干活"。

### 1.4 清单：App 怎么被知道

框架不知道有哪些 App，除非有人告诉它。这个"告诉"就是**清单**：一份 `const app_desc_t *const` 数组。

```c
/* apps/app_manifest.c —— tag 1 与 tag 2 共写，只许在数组末尾追加 */
static const app_desc_t *const s_apps[] = { &g_app_yourname };

const fw_manifest_t g_manifest_aiapp = { s_apps, sizeof s_apps / sizeof s_apps[0] };
```

`fw_init(const fw_manifest_t *manifests, uint32_t count)` 把 N 份清单合并进注册表并查重 id；`count = 1` 时入口自己拼成一个大数组，`count = N` 时按作者各给一份（决定 33，见 [code-structure.md](code-structure.md) §12）。

清单本身的类型（`framework/include/fw_init.h`）：

```c
typedef struct {
    const app_desc_t *const *apps;   /* 指向 app_desc_t* 数组的首元素 */
    uint32_t                count;   /* 数组元素个数 */
} fw_manifest_t;
```

两个字段都不可省：`apps + count` 是"数组 + 长度"的唯一表示，不能靠 NULL 结尾（`NULL` 是合法的 `app_desc_t *`，用它当哨兵会让查重 id 漏掉一个 App）。

**没写进清单的 App，编译好了也不会启动。** 这是"AI 加一个 App"能成为可门禁动作的原因：清单只许追加、且新增行只许引用自己目录下的对象（[access-control.md](access-control.md) §4.3）。

清单为什么按作者分多份、而不合成一份：单一表会逼 AI 的注册单元 `extern` 系统 App 的 `app_desc_t`——既越权，又脆弱。

## 2. 管理器 App（id 1）—— 属产品仓库

> **术语**：本章标题里的"0 号"是历史叫法，`app_id_t` 是 **1**（见文首「术语约定」）。
>
> 本节描述的是**架构角色**，不是本仓库的代码。本仓库不提供管理器实现（见 §0）。
> 框架只做两件事：拉起 `APP_FLAG_SYSTEM` 的 App、提供 `fw_app_*` 控制面。

| 职责     | 说明                                                                           |
| -------- | ------------------------------------------------------------------------------ |
| 引导     | 由 `fw_boot()` 按 `APP_FLAG_SYSTEM` 拉起（不是 `app_main()` 创建的；`fw_init()` 是 `app_main()` 调的）。就位后接管启动编排 |
| 启动编排 | 读所有清单，按 `requires` 的拓扑序决定启动谁、什么顺序（**`requires` 目前没有存放位置**，见 §11.1） |
| 配额预检 | 累计 `stack_bytes` / `psram_bytes`，超预算在启动前拒绝（**这两个字段同样没有存放位置**，见 §11.1） |
| 能力汇总 | 读能力位，生成运行时能力表，供 App 查询"本机有没有麦克风"                      |
| 监控     | 心跳 / 提交超时 / 队列积压；异常先标记 `FAILED`，不直接杀                      |
| 停止     | 协作式（§1.2），逆拓扑序                                                       |
| 故障隔离 | `FAILED` 的 App 不再收到投递，依赖它的 App 收到明确错误码                      |

**管理器 本身只是一个 App**，特殊在"它是唯一能启动别人的人"，而非权限。框架层因此仍然没有运行权。

## 3. 接口契约

### 3.1 三条铁律

**铁律一：框架提供的一切阻塞都是伪阻塞，退出由框架负责。**

App 看到的是普通阻塞函数，看不到"停止"这件事：

```c
int  stor_read(int fd, void *buf, size_t n);   /* 会阻塞 */
void fw_delay_block(uint32_t ms);                   /* 也会阻塞 */
```

框架在其内部实现伪阻塞：

```c
int stor_read(int fd, void *buf, size_t n) {
    int r = pf_storage_read(fd, buf, n);     /* 内部按块等待，每块查取消位 */
    release_internal(fd);                    /* ① 先让自身资源回到一致状态 */
    if (fw_cancelled()) fw_run_exit();     /* ② 再检查退出码，不返回 */
    return r;                                 /* ③ 未取消才正常返回 */
}
```

> 上面代码里的 `fw_cancelled()` / `fw_run_exit()` 属于**机制面**（`framework/include/fw_app.h`），
> AI 写的 App 看不到它们——它们只出现在框架自己的阻塞点实现里。App 面（`api/af_api/`）
> 只暴露 `fw_delay_block()` 这个"会响应停止的延时"，连"取消"这个词都不出现。

**App 不检查返回值、不写状态机、不轮询。** 它写直线代码。这是对 AI 最友好的形态：取消语义完全藏在框架里，AI 不需要为"随时可能被停"设计任何结构。

取消位放在**任务上下文**里：管理器 置位，任务在退出时自己清零。App 侧不提供读取它的 API——需要保存状态就写 `exit()`。

与原表述的差别：原来禁止"阻塞超过 1ms"，现在禁止**不可打断的阻塞**。危险的不是等待，是等不回来。

**铁律二：应用层接口一律「提交即返回、最终一致」。**

```c
cm_err_t disp_commit(const page_t *page);   /* 立即返回，同 key 覆盖 */
```

提交 10 次只刷最后 1 次，是**实现层的职责**，不是 AI 的修养。推论：**AI 没有"刷新"这个动作可用**，从结构上做不到刷坏屏。

需要结果时可以等完成事件——同样是伪阻塞，可被停止打断。

**铁律三：阻塞点只能落在事务边界上。**

框架的阻塞点不得出现在器件时序中间——屏幕的半帧、SD 卡的半个扇区、一段 I2C 复合事务。这些必须在一次不可打断的段内做完，再回到可取消的边界。

#### 3.1.1 退出路径

```
阻塞点发现取消位
  → 标记"正在退出"
  → 立即清取消位（= 在 exit() 期间禁用取消；放在 exit() 之后是 bug，见下）
  → 调 App 的 exit(ctx)（可选：存阅读进度、落盘草稿）
  → 框架回收本 App 的托管资源（`res_track` 登记过的槽位）
  → 置终态（STOPPED / FAILED）
  → 结束任务，不返回调用者
```

**"先清取消位、再调 `exit()`"这个顺序不能反。** 若先 `exit()` 后清位，`exit()` 期间取消位仍是置位的：清理里任何一次阻塞调用（一次 `fw_log`、一次落盘）都会再次命中取消位、再次进入退出路径，清理永远走不完——这正是第 3 条硬约束（退出期间禁用取消）要防的东西。

**因此资源必须登记在 ctx 上，不能只放在栈上。** 退出可以从任意一个阻塞点发起，那时看不到上层栈帧的局部变量：

```c
/* 对：获取与登记是一次原子动作 */
res_track(&ctx->book_fd, stor_open(path, O_RDONLY));

/* 错：open 返回与赋值之间若被取消，fd 永久泄漏 */
ctx->book_fd = stor_open(path, O_RDONLY);
```

推论：**框架的资源获取接口直接写 ctx 槽位**，App 不持有裸句柄。托管资源的回收由框架代劳，`exit()` 只剩业务清理。

#### 3.1.2 四条硬约束

| #   | 约束                                                        | 不满足的后果                          |
| --- | ----------------------------------------------------------- | ------------------------------------- |
| 1   | 每个阻塞点必须可取消                                        | 停止延迟无上限                        |
| 2   | 单段不可打断的等待 < 200ms                                  | 停止延迟 = 当前段长度，超过用户可感知 |
| 3   | 退出处理期间禁用取消                                        | 清理中被再次取消 → 永不结束           |
| 4   | 只有 App 任务有取消位；平台任务 / 框架初始化 / ISR 不可取消 | 在不可取消的上下文里长阻塞 = 卡死整机 |

第 2 条是唯一能自动检查的：**停止延迟 = 当前阻塞段长度**。这是结果指标，不是手段指标，所以能进门禁。

#### 3.1.3 取消位的生命周期

管理器 置位 → 阻塞点发现并生效 → 任务退出时清零 → 管理器 确认 `STOPPED` 后才允许重启。

**顺序不能反**：若重启前不清零，新任务在第一次阻塞就立刻被杀，表现为"App 起不来"。清零只有任务自己知道确切时刻——这就是"task 自己清理"的必要性。

#### 3.1.4 停止的是 App，不是它已提交的操作

`disp_commit()` 之后操作归 display App 所有；调用者被停止，屏幕继续刷完。否则中断落在刷屏中间是硬件风险。撤销只能用 `disp_cancel(token)`，且只在安全点生效。

#### 3.1.5 死循环不算阻塞

`while (1) { work(); }` 里若没有任何伪阻塞调用，取消位永远不会被看到。

**防线只有两道**：

1. **门禁静态检查**：任务体内必须至少有一个伪阻塞调用（`fw_delay_block` 也算）。
2. **心跳看门狗**：超时未心跳则把 App 标 `FAILED`（管理器策略）。

两道防线都只能覆盖"调用了框架接口的 App"。**一个纯死循环的 App，框架发现不了，只能靠重启整机恢复。** 这是 AI 写 App 最常见的错误形态，也是本套件收的第一优先级风险；写 App 时把"任务体内必须有 `fw_delay_block`"当硬规则。

### 3.2 接口分类

| 类型                         | 形态                              | 阻塞                   | 例子                        |
| ---------------------------- | --------------------------------- | ---------------------- | --------------------------- |
| **提交型**（有状态、长时序） | 投递给 owner，立即返回 + 完成事件 | 否（可自愿等完成事件） | `disp_commit`、`audio_play` |
| **同步型**（无状态、短）     | 直接函数调用，内部自带锁          | 伪阻塞，可被停止打断   | `stor_read`、`rtc_now`      |
| **延时型**                   | `fw_delay_block(ms)`                   | 伪阻塞，按时长分块     | 轮询、动画节拍              |
| **共享流型**（唯一实例）     | 无参数 obtain/release + 引用计数  | 否                     | `mic_obtain`                |

### 3.3 共享资源：不暴露参数

硬件只有一个采样率、一个格式。**接口里就不应该有参数**——没有参数，就不存在"参数不同无法共享"。

```c
mic_h   mic_obtain(void);        /* 无参数；格式由平台定死 */
void    mic_release(mic_h h);
size_t  mic_read(mic_h h, void *buf, size_t n);
```

不提供 `mic_init()`：**没有初始化接口，就没有"谁来初始化、初始化成什么"的协商**。需要别的格式的 App 自己重采样，接口不为此让步。

### 3.4 锁：归请求者，只用于短临界区

| 临界区长度  | 谁持锁         | 形态                                |
| ----------- | -------------- | ----------------------------------- |
| < 1ms       | **请求者**     | `res_lock(); op(); res_unlock();`   |
| 1~100ms     | **请求者**     | try-lock + 超时，失败立即返回错误码 |
| **> 100ms** | **不允许用锁** | 提交给 owner，立即返回 + 完成事件   |

判据：**别人能不能容忍等这么久**。等 3 秒刷屏不是锁能解决的，是调度问题，因此它根本不该以"锁"的形态暴露。

`res_lock()` / `res_unlock()` 的声明和其他资源接口放在一起（§5）。它们是**伪阻塞**的：等锁期间取消位一旦命中就返回 `CM_ERR_CANCELLED`，并保证此时**没有持锁**——否则退出路径会在持锁状态下走下去。

### 3.5 不设优先级分带

时间片 1ms 远小于音频 DMA 缓冲（32ms）与触摸采样周期（10ms），同优先级不会造成可感知抖动。

- 所有 App task 用同一个常量优先级，**低于平台自身的系统任务**（ESP32 上是 Wi-Fi/蓝牙等系统任务）；
- **不提供**设置优先级的接口 —— 不是靠禁令，是靠没有入口。`pf_rtos_t.task_set_priority` 是**平台侧**的能力：框架用它把 App 任务放到那个固定优先级上（以及给平台内部任务调层级），不向应用层暴露。
- 真正危险的是**关中断**和**忙等不 yield**，那是 §7 的独立规则。

### 3.6 服务的落点：注册表

`api/` 里的功能分两类，实现位置不同，但**对调用方完全一样**：

| 类别   | 例子                                    | 实现在哪          |
| ------ | --------------------------------------- | ----------------- |
| 机制型 | `stor_open`、`res_acquire`、`fw_delay_block` | 框架层            |
| 服务型 | `disp_commit`、`audio_play`             | 服务 App + 注册表 |

服务型 API 的实现体在 App 里，但**函数符号属于框架**：框架的转发层持有函数指针，做三件事后转给服务：

1. 未注册 → `CM_ERR_NOT_SUPPORTED`（这块板没有这个能力）
2. 已注册但服务 `FAILED` → `CM_ERR_UNAVAILABLE`（崩了，可重试）
3. 调用返回前检查取消位 → 已取消则走退出路径

**1 和 2 必须分开**：把"没有这个能力"和"有但暂时坏了"混成一个错误码，UI 就无法区分"隐藏入口"和"提示重试"。

这样做的原因只有一条：**伪阻塞的保证必须落在一处**。若让每个服务自己导出符号，"每个阻塞点都可取消"就从保证退化成"每个作者各自记得做"。

两个次生结论：

- 两个 App 之间不需要互相 include，也不需要知道对方存在；
- 管理器通过注册表就知道"谁提供了什么、现在什么状态"，不必认识任何 App。

## 4. 冲突模型（三层）

硬件唯一性造成的冲突分三层，裁决者与可见性不同：

| 层         | 冲突对象                                          | 裁决者                   | 对应用层可见 |
| ---------- | ------------------------------------------------- | ------------------------ | ------------ |
| **逻辑层** | 谁在用"喇叭/麦克风/屏幕"这个**功能**              | 管理器 + 应用层锁       | **可见**     |
| **器件层** | 同一器件的**一整段时序**不能被切开                | 驱动内部会话锁           | 不可见       |
| **总线层** | 同一物理总线 / DMA / 引脚上的**单次事务**不能交错 | 平台层，读自己的板级描述 | 不可见       |

**应用层的锁不映射到总线锁。** 应用层只知道"我要显示这一页"，不知道底下有没有和 flash 抢 SPI。若让应用层管总线锁，换一块板（总线拓扑不同）就要改所有 App。

总线仲裁是**平台包的内部实现**，两级锁都不能省：器件会话锁保护一整段时序，总线锁保护单次事务。

## 5. 资源接口

```c
/* 只用于"连续的一块内存"：PSRAM、内部 RAM、task 栈 */
res_h_t  res_acquire(res_kind_e kind, size_t bytes, res_life_e life);
void     res_release(res_h_t h);

/* 用于"不是内存的东西"：文件句柄、信号量、总线会话 —— 没有 bytes 这个维度 */
void     res_track(void *slot, void *handle);   /* 写进 ctx 槽位，退出时框架自动关 */

/* 应用层锁（§3.4）：只用于 < 1ms 的临界区，伪阻塞 */
cm_err_t res_lock(res_id_t id);                 /* 取消位命中 → CM_ERR_CANCELLED，且未持锁 */
void     res_unlock(res_id_t id);
```

**两类东西不能共用一个签名。** 早期版本让 `res_acquire` 同时覆盖"文件句柄"和"总线使用权"，但 `bytes` 对句柄没有意义，对总线更是错的——总线是平台层内部的两级锁（§4），**应用层拿不到、也不该拿到总线使用权**。已拆成上面两个入口。

**只做记账与限额，不重造分配器**：`framework/` 自己不调用任何分配器，真正的分配发生在平台的 `pf_ops_t.mem_alloc` 里；在 ESP32 上它通常是 `heap_caps_malloc(MALLOC_CAP_SPIRAM)`，在 host-fake 上是 `malloc`。`framework/` 只记"谁申请了多少、退出时还欠多少"。这样纯度门禁（`framework/` 不得出现 SDK 标识符）与"不重造分配器"两条同时成立。

> 自己实现 buddy/slab 会带来碎片率、PSRAM 访问延迟和一套没人维护的分配器。配额、冲突、回收因此只有一个落点：平台层的 `mem_alloc`。

## 6. 框架不规定任务数量

"每个硬件一个 task"是**平台实现的事**。框架只规定两件：

1. **task 只能由框架创建**：`fw_task_create()` 内部使用固定优先级常量，App 接触不到 FreeRTOS 优先级；
2. **主任务必须事件驱动、有界等待、可协作退出**（§1.1）。

给平台实现者的判据：**这个外设有没有排他性的长时序状态**？有才建 task；没有就是一个库函数 + 内部锁（纯寄存器类器件通常都不需要自己的 task）。

## 7. 门禁与 skill 硬约束

「AI 不可信」「AI 不能改应用层以外」必须落成机器能查的，否则只是文字。

### 7.1 机械门禁（CI）

| 门禁             | 检查方式                                                                                    | 防的是什么                                                                               |
| ---------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 写入白名单       | `git diff --name-only` 逐个查 `policy.txt` 的写权限（`check_policy.py --as <tag\|human>`，三条判定都跑） | AI 改框架层/平台层                                                                       |
| 依赖判定         | `clang -M` 的真实解析结果逐个查读权限                                                       | 越权 include（`../`、`-I`、`#include_next` 都绕不过真实解析）                            |
| 符号判定         | `llvm-nm -u` 的未定符号，要么其**定义**在调用者可写区，要么声明在**调用者不可写**的头里     | `extern void fw_boot(void);` 这类不 include 就取特权；也包括"在自己可写的头里造一份声明" |
| 解耦检查         | `check_purity.py`：app 不碰 SDK、platform 不碰业务                                          | 跨层调用 / 平台耦合                                                                      |
| 例外白名单       | platform 只调 `fw_event_post` / `fw_event_post_isr`                                         | 反向调用扩大化                                                                           |
| 能力目录双向比对 | 已发布的 `api/af_api/*.h` ⇔ 目录条目 ⇔ 某个 service 注册的操作，三者必须一一对应 | 手写文档漂移 → AI 调不存在的接口，**且失败是静默的**。v1 不含屏幕、`disp.h` 不发布，所以目录里本就没有显示条目——**"没发布"不算漂移** |
| 交付格式固定四行 | `Build` / `Host tests` / `Device tests` / `Unverified`                                      | 把编译成功说成硬件验证成功                                                               |
| host 单测        | `cc -std=c11 -Wall -Wextra -Werror` + `platform/host-fake/` 编进 PC 一起跑                | 框架层是纯逻辑，必须离线可测                                                             |

### 7.2 skill 硬约束

- 只能修改 `policy.txt` 允许的路径（本仓库是 `apps/demo/` 与 `apps/app_manifest.c` / `.h`）；越界立即停止并报告。
- 主任务必须事件驱动、有界等待、有协作退出检查点。
- **禁止** `xSemaphoreCreateBinary` 当锁（无优先级继承）；用 mutex。
- **禁止**忙等 / 关中断超长；长计算必须让出 CPU。
- **禁止**调用设置 task 优先级的接口（框架也没有提供）。
- **禁止** include `platform/` 与 `framework/`，只能 include `api/af_api/` 与 `common/`（`framework/include/` 只对系统 App 开放）。
- 共享资源必须 obtain/release 成对，且不得假设能改格式。
- **使用任何能力前先查 `cap_available()`**，不得假设本平台一定有；降级路径必须靠**接收返回值**来写，不能只靠预先查询。能力位的来源是平台契约里的可选成员 `pf_ops_t.caps()`（`uint32_t` 掩码，返回 0 或成员为 NULL 都表示"未声明"→ 一律当作没有）；`cap_available()` 是它的框架侧只读缓存，启动时取一次；**位定义见 §7.3**。
- 屏幕：不得在应用层请求"全刷"，没有这个接口。
- 每轮完整实现后**必须主动询问是否烧录真机测试**（设备已连接 ≠ 烧录授权）。

### 7.3 能力位定义

`pf_ops_t.caps()` 返回一个 `uint32_t` 掩码，位定义写在 `platform/port/pf_ops.h`。每一位回答的是**"这块板有没有这件硬件"**，不是"接口发布没发布"——后者由编译期决定（头在不在）。所以 v1 里 `PF_CAP_DISPLAY` 可以是 1，而 `api/af_api/disp.h` 并不存在：查得到硬件，不代表有接口可调。

| 位 | 宏 | 含义 |
|---|---|---|
| 0 | `PF_CAP_DISPLAY` | 有可显示的屏（显示服务可注册） |
| 1 | `PF_CAP_DISPLAY_PARTIAL` | 屏支持局刷（`PF_CAP_DISPLAY` 未置位时无意义） |
| 2 | `PF_CAP_TOUCH` | 有触摸输入 |
| 3 | `PF_CAP_KEY` | 有物理按键/旋钮 |
| 4 | `PF_CAP_STORAGE` | 有持久存储（文件系统可用） |
| 5 | `PF_CAP_NET` | 有网络（Wi-Fi 或以太网） |
| 6 | `PF_CAP_AUDIO_OUT` | 有扬声器/耳机输出 |
| 7 | `PF_CAP_AUDIO_IN` | 有麦克风输入 |
| 8 | `PF_CAP_RTC` | 有带电池的硬件 RTC |

9–31 **保留**：未定义的位必须读出 0。平台返回未定义的位是真值也算缺陷（与"九项里填了不该填的立刻可见"同一个原则：不要让没被设计过的值悄悄生效）。

### 11.2 三个待议议题

**T4 平台包怎么引入**

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（建议）** | 各平台就是 `platform/<板>/` 子目录，与框架同仓 | 平台适配者要拿到整个仓库；好处是 `tests/port/` 与被测平台永远同版本 |

| **A（建议）** | ESP32 全系（FreeRTOS 一族）+ host-fake | 接 Zephyr / 裸机要另做一层 |
| B | 任意 RTOS | `pf_rtos_t` 要膨胀成通用 OSAL，每个成员都要在每条路径上重新论证 |
| C | 连裸机也覆盖 | 需要自己实现任务调度，等于写半个 RTOS |

建议 A：**不为假想中的第三族预先付代价**。

**T6 崩溃 / 死循环兜底归谁**

| 选项 | 分工 | 代价 |
|---|---|---|
| A | 全在本仓库 | 本仓库只有设计，没有心跳源；框架本身没有运行权，喂不了狗 |
| B | 全在产品仓库 | 框架侧不提供任何"可被观测的心跳"，产品仓库要自己从头想 |
| **C（建议）** | 分工：本仓库负责"让 App 能被停下来"（伪阻塞 + 门禁 + 状态位），产品仓库负责"发现它停不下来时动手"（心跳看门狗 + 重启策略） | 需要两边都实现才闭环 |

子问题：**心跳谁喂？** 两个选项——App 自己喂（多一条硬规则，AI 容易漏）；或框架在 `fw_delay_block()` 与提交型接口里自动喂（倾向这个：**喂狗时机本来就是阻塞点，而阻塞点全在框架手里**）。这一条还没定。
