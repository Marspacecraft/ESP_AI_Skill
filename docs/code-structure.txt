# code-structure —— 未定与未实现事项

> 本文件记录 [code-structure.md](code-structure.md) 里所有"还没定、还没做、有歧义"的内容。设计结果在 md 里（定稿 v1.0）。

## 对应 md §0：目录树与 policy.txt 的对照靠人读

目录树里每一行都标了归属（`tag N 写` / `人维护`），但它和 `policy.txt` 的一致性**只做了弱校验**：`check_structure.py` 现在比对的是"每条 `policy.txt` 前缀在 md 里出现过、每个已存在的顶层目录有人能写"，**不解析 Markdown 表格里的逐行归属**。所以"某一行标的 tag 写错了但前缀名对得上"仍然查不出来——那部分还是靠人读。

## 对应 md §1：仓库根的新顶层目录没有人能写

`policy.txt` 里没有任何一行覆盖仓库根目录，所以根下**新建**一个顶层目录（例如 `scripts/`）不属于任何 tag——谁都不能写。这是刻意的（新增顶层目录等于新增一处结构，必须人批准），代价是人忘了加行时表现为"莫名 Permission denied"。

## 对应 md §2.1：`cm_tls` 在平台契约里没有位置

`cm_tls.h` 只给声明，实现依赖各平台：host-fake 用 C11 `_Thread_local`，ESP32 要用 FreeRTOS 的 task-local-storage 指针（裸任务的 TLS 初始化不会自动发生）。而 `pf_ops_t` 九项里**没有 TLS 项**——所以"实现落在哪"没有契约依据，只能由 tag 4 在自己平台目录里给。

## 对应 md §3：`api/` 里只有五个头有设计

`api.h` / `app.h` / `log.h` / `res.h` / `cap.h` 五个有设计；`disp.h` / `input.h` / `audio.h` / `stor.h` / `net.h` / `power.h` **连设计都没有**（屏幕的 `disp` 是单独立项，见 [display.md](display.md)）。所以现在一个可 include 的能力头都没有。

## 对应 md §4.1：注册不会早于调用方

"服务 App 在自己的 `init()` 里注册，早于任何调用方启动"这条顺序**由 `requires` 拓扑排序保证，而拓扑排序未实现**——当前只能按清单顺序。清单顺序写错时，调用方会先跑起来并拿到 `CM_ERR_NOT_SUPPORTED`，看起来像"板上没这能力"。

## 对应 md §8：公共驱动的接口形态未定

`platform/drivers/` 已定（tag 5 写），但**驱动对外暴露什么形态没定**：是 `open/read/close` 一套会话函数，还是"填一张配置表 + 纯函数"（md §8.1 的示例倾向后者）。这决定板级目录写多少代码。

## 对应 md §9/§10：门禁与测试入口已实现，构建入口还没有

`tools/` 里的门禁脚本**已经实现**（`python tools/validate.py` 当前 PASS），`tests/test.py` 也已实现并能跑（`python tests/test.py tools` → 12 条全 PASS）。仍然不存在的：

- **没有 `CMakeLists.txt`**：`idf.py build` 与"把测试编进固件"都跑不起来。
- **`tests/` 下只有 4 个文件**（`test.py`、`tinytest.h`、`tinytest.py`、`tools/test_gates.py`）。`tests/support/` 夹具与各层的 `test_*.c` 都还没写——目录树里画了，不代表存在。
- **`tests/port/pf_conformance.c` 还没写**：它要 `platform/port/pf_ops.h`，而那个头也不存在。

所以 **`validate.py` 通过只说明"检查器自己是对的"，不说明"代码是对的"**——其中 6–7 步是 `SKIP`。测试框架的设计见 [test-plan.md](test-plan.md)，缺口见 [test-plan.txt](test-plan.txt)。

## 对应 md §10：九个门禁脚本的状况

九个脚本都已落盘：`check_policy.py`、`check_purity.py`、`check_blocking.py`、`gen_catalog.py`、`check_catalog.py`、`check_layers.py`、`run_tests.py`（**已降级为 `tests/test.py` 的转发壳**）、`validate.py`、`check_structure.py`（另加 `policy.py`、`common.py`、`purity_rules.txt`）。测试入口与断言头在 `tests/`，不在 `tools/`。

仍然要记住的边界：

- **`check_blocking.py` 只做静态匹配**（任务体里有没有阻塞调用、有没有"无限循环 + 无阻塞"），**不是运行时保证**。纯死循环仍然只能重启整机，看门狗不在本仓库（见 [architecture.md](architecture.md) §11.1）。
- **仓库没有任何 git 提交时，写入判定会打印 `SKIP`**；`check_structure.py` 的"目录树 ↔ `policy.txt`"是**文本比对**，不解析 Markdown 结构。
- 所有脚本**都没有单元测试**——它们自己就是被验证的手段，而门禁本身没有门禁。

### `check_policy.py` 还要查的两件事

1. **注册清单只许追加**：`git diff` 该文件只增不删，且新增行只引用 `apps/demo/` 下的对象。（**未实现**）
2. **每个已存在的顶层目录必须被某个 `role` 前缀覆盖**，否则报错。（**已实现**，`check_structure.py` 与 `check_policy.py` 都会报 `STR-ORPHAN` / `T-ORPHAN`）

## 命名迁移（已定，未执行）

`plat_ops_t` → `pf_ops_t`、`plat_ops.h` → `pf_ops.h`（**该路径在 `policy.txt` 里，改名须走评审**）、`PLAT_MUTEX_FOREVER` / `PLAT_OPS_STUB` → `PF_*`、`plat_state_t` → `pf_state_e`、`plat_conformance_run` → `pf_conformance_run`、六个 `app_*`（`app_delay`/`app_cancelled`/`app_run_exit`/`app_log`/`app_alloc`/`app_task_create`）→ `fw_*`、枚举 `_t` → `_e`。

注意：①一次做完，半迁移比不改更糟；②`plat_ops.h` 牵涉 `policy.txt`，必须与文档同步；③迁移完成前，规范与代码不一致是**执行债**，不是规范错。

## 还开着的三个小问题（需裁决）

1. **状态枚举的正式名字**：文档里状态写的是 `EMPTY` / `INIT` / `RUNNING` / `STOPPING` / `STOPPED`，但**没有定义枚举类型名与取值前缀**。`coding-style.md` 要求枚举值全大写带层前缀，所以最终大概会是 `FW_STATE_RUNNING` 一类。定下来之前，代码示例里一律用裸 `RUNNING`。
2. **`fw_app_count()` / `fw_app_at()`**：只在 [app-model.md](app-model.md) 的目录树注释里出现过一次，`framework/include/` 五个头的职能表里没有。要么把它们写进 `fw_app.h`，要么改成"管理器自己遍历 `fw_manifest_t`"。
3. **延时能力的两个名字**：`pf_ops_t.sleep_ms`（平台契约九项之一）与 `pf_rtos_t.delay_ms`（RTOS 原语表）是同一件事的两个名字。要么只保留一个（`pf_rtos_t` 那份），要么在契约里写明"平台只实现一次、两个成员指向同一份实现"。
