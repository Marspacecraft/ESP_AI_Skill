# 屏幕（v1.0）

> **状态：定稿 v1.0（2026-10-30）**
>

>
> 屏幕上**一行代码都没有**：`api/af_api/disp.h` 不存在，`platform/` 里没有刷屏实现。

## 1. 为什么单独成文

屏幕是本架构里**唯一**一处"应用层语义与平台物理特性强耦合"的地方：

- 刷新是**长时序状态**——一次全刷 1~2 秒，期间不能改屏上正在刷的那份数据；
- 有**残影**，而残影不是"画质问题"，是"刷了不该刷的东西"；
- 局刷能力**逐板不同**，没有局刷的板上"只刷一小块"根本做不到；
- 波形与上电时序**不可中断、不可重排**。

用通用平台契约（`pf_ops_t`）表达这些，会把每块平台都拖进"刷新模式词汇该有几个"的分歧里。所以屏幕单独一份文档、**独立版本号、独立评审**：它演进得快，不该拖住框架层。

## 2. 范围

- **v1 不含屏幕。** 这是范围定案，不是"还没写"——v1 通过时，App 在屏幕上什么都不会显示，因为 v1 只证明三件事：App 能被拉起来、能被停下来、`exit()` 恰好一次（[app-model.md](app-model.md) §7 的六条）。
- **`api/af_api/disp.h` 在 §7 的问题定下来之前不存在。** 在它发布之前，任何人都不要引用 `disp_*`。
- 本仓库负责：应用层接口、提交合并、damage 管理、刷新策略的上层决策。
- 平台负责：波形、上电时序、SPI 传输、面板参数、物理缓冲。

## 3. 谁负责什么

| 层 | 负责 | 明确不负责 |
|---|---|---|
| 应用层（tag 1/2） | 决定"显示什么"、什么时候提交 | 刷新模式的实际执行、波形、传输 |
| 本仓库（tag 5 接口 + 框架） | 提交型接口、同 key 合并、damage 累积、token 与完成事件 | 任何面板时序 |
| 显示服务 App（tag 1，产品仓库） | 把提交翻译成平台调用、排刷屏队列、决定什么时候清残影 | 画什么内容 |
| 平台层（tag 4） | 波形、上电时序、SPI、面板参数、物理缓冲 | 内容语义、排版 |

**分界线**：凡是"换一块屏就要改"的东西，一律在平台层；凡是"换一个 App 就要改"的东西，一律在应用层。中间那层（什么时候刷、刷哪块）是本仓库与显示服务的事。

## 4. 应用层看不到"刷新"

三条铁律（[architecture.md](architecture.md) §3.1）在屏幕上一体适用，并且更严格：

- **提交即返回**：`disp_commit` 立刻返回，刷屏在框架/服务的任务里做。一次全刷 2 秒，绝不允许把 App 的主循环钉住。
- **同 key 覆盖**：连续提交同一个显示区域，只有最后一次生效——AI 结构上做不到"刷坏屏"。
- **没有"请求全刷"的接口**。全刷是残影管理的一部分，由服务决定，不由 App 请求。这条在 [architecture.md](architecture.md) §7.2 已经是硬约束。
- App **不得**直接写 SPI、不得自己算波形时间、不得假设某个刷新模式一定存在（查 `PF_CAP_DISPLAY` / `PF_CAP_DISPLAY_PARTIAL`，见 [architecture.md](architecture.md) §7.3）。

## 5. 接口面（占位，未发布）

以下名字**只是占位**，签名未定、头文件不存在。列在这里是为了让其它文档有东西可引用，不代表任何承诺：

| 占位名 | 大致形态 |
|---|---|
| `disp_commit` | 提交一帧/一块，返回 token |
| `disp_cancel` | 取消未完成的提交 |
| `disp_token_t` | 提交标识，用来匹配完成事件 |
| `page_t` | 一屏的内容载体 |
| `damage` | "哪块区域变了"的描述 |
| ~~`disp_err_t`~~ | **不设**：错误码全项目统一用 `cm_err_t`（`common/include/cm_err.h`），分层自定义错误码已被否决 |

这些名字的最终形态取决于 §7 的裁决：切分粒度决定 `page_t` 是什么，刷新模式词汇决定 `disp_commit` 的参数，双缓冲决定 token 的语义。

## 7. 待议问题（暂存）

> 本节是本文档**唯一**允许存放"还没定"的地方（因为屏幕是独立立项的单文件组件）。
> 每条都给选项与当前倾向；**没有裁决的不算设计结果**，实现时不要按"倾向"当定论。

### S1 切分粒度：应用层画什么、平台怎么切

- **A** 应用层提交**整屏位图 + damage 矩形**，平台自己决定分块与传输节奏。
- **B** 应用层按 **band**（如 32 行一条）提交，平台逐条刷。
- **C** 应用层提交**页面描述**（文本 + 图元），平台负责排版与渲染。

倾向 **A**：墨水屏 App 绝大多数是"文字页 + 少量图"，位图最通用、与刷新策略完全解耦；C 会把排版与字体渲染塞进平台层，`platform/` 立刻要懂字形与断行；B 把面板带宽特性漏进应用层，换一块屏 App 就得改。

**若选 A 还有两个子问题**：

1. 一屏怎么放得下——480×800 单色 = 48 KB，8 位灰度 = 384 KB，后者必须按行或 damage 分片提交。分片是对外可见的（`page_t` 形态随之改变）还是内部的？
2. 全屏缓冲归谁——框架托管（那它算不算 `res_acquire` 的配额？）还是显示服务自己 `res_acquire` 一块？

### S2 刷新模式词汇表

- **A** 只有 `DISP_REFRESH_FULL` 与 `DISP_REFRESH_FAST`。
- **B** 再加 `DISP_REFRESH_PARTIAL`（要求 `PF_CAP_DISPLAY_PARTIAL`）。
- **C** 再加 `DISP_REFRESH_GHOST_CLEAN`（清残影）。

倾向 **B**：清残影不是独立模式——它就是一次全刷，多一个词只会让 AI 在同一件事上选错。模式越少，AI 越不容易写出"看起来对但刷得很难看"的代码。

**子问题**：模式是 `disp_commit` 的一个参数，还是不同函数（`disp_commit` / `disp_commit_fast`）？前者少一套函数、多一个必填枚举；后者读起来直白但会随模式增加而膨胀。

### S3 撕裂与双缓冲

- **A** 不做双缓冲：应用层提交 → 框架拷进**平台侧刷屏缓冲** → 屏从它刷，刷期间不接受新提交。
- **B** 框架再持一份 shadow buffer（PSRAM），刷完才拷。

倾向 **A**：单 MCU 上"刷的时候不能改那份缓冲"是硬件事实，B 多占一屏内存（48–384 KB）只换来让应用层早 20 ms 拿到提交返回——而这个需求已由"提交即返回 + 完成事件"解决了。

**子问题**：刷期间新提交是"覆盖待刷内容"（内存里那份还没传到屏，可以改）还是"等这次刷完再说"？两者对 `disp_token_t` 的语义不同。

### S4 IO 与刷新耦合

- **A** 串行：提交 → SPI 传输 → 等波形结束 → 完成事件。
- **B** 允许后台传输：提交后立刻返回 token，传输与波形在框架任务里跑。

倾向 **B**，与"提交即返回"一致（否则一次全刷 2 秒会把 App 的主循环钉死）。

**子问题**：刷屏期间又来一次提交怎么办——**覆盖**（同 key 覆盖，与提交型接口一致，倾向这个）还是**排队**（队列深 1，满了返回 `CM_ERR_BUSY`）。

### S5 没有局刷时的降级

- **A** 返回 `CM_ERR_NOT_SUPPORTED`。
- **B** 静默降级成 `FAST`。

倾向 **A**：静默降级让"我只刷一小块"的性能预期落空，且症状是"这板子怎么这么慢"，几乎查不出来。配合 `cap_available(PF_CAP_DISPLAY_PARTIAL)` 先查，选择权留在应用层。

### S0 尚未讨论的边界（还没列成选项）

1. **damage 由谁算**：应用层自己给矩形，还是框架比对前后两帧算差分？前者省 CPU、可能漏；后者准确、要两份缓冲。
2. **完成事件**：走 `fw_event_post`（唯一反向例外）还是单独的 per-token 回调？前者统一，后者省一次查表。
3. **多 App 抢屏**：两个 App 都提交了，谁先上屏？按 App 优先级、按提交顺序，还是"前台 App 独占"（那就需要前台/后台概念，而 App 模型里没有）。
4. **应用层的"整屏"长什么样**：一行多少像素、色深几位、坐标系原点在哪——这些一旦定了就是对外契约，改起来极贵。
5. **文字渲染**：字体、点阵、断行、抗锯齿由谁做？如果由 App 做，每个 App 都要一份排版代码；如果由框架做，屏幕就变成"页面描述"形态（与 S1 选项 C 相关）。
