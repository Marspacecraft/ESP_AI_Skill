# 服务号登记表（service ids）

**这张表与代码是双向绑定的**：`tools/check_svc_ids.py` 同时读这张表和 `api/af_api/*.h`，
任何一边漏写、号写错、或两个服务抢同一个号，`./build.sh run` 就红。

它回答一个问题：**这个服务号被谁领了，还有没有第二个代码在用它。**

## 为什么需要这张表

`fw_svc_id_t` 是 `uint8_t`，**谁都能挑号**。撞号时唯一的症状是运行时
`fw_svc_register()` 返回 `CM_ERR_BUSY`、第二个服务永远起不来——而编译期、CI、
代码评审都不会提一个字。两个 agent 各写各的服务时，这是最容易发生、也最难查的一类事故。

能力位有 `docs/generated/catalog.md` 盯着（位号写错门禁会红），服务号必须有同样的东西。

## 三条规则

1. **先领号，再写代码。** 号写进该服务的接口头，形如 `#define DISP_SVC_ID 2u`，
   全仓只此一处定义。表里补上一行，两处必须一致。
2. **号段分区**（`docs/cross-repo.md` 的第四个"合并时最容易出问题的地方"）：

   | 号段 | 归属 | 说明 |
   |---|---|---|
   | `0` | 保留 | `FW_SVC_NONE`，永远不是有效服务 |
   | `1–127` | **本仓库** | 框架自带 / 平台相关的服务 |
   | `128–255` | 产品仓库 | 例如 ai-passport 自带的业务服务；本仓库的表不登记它们 |

   分区的原因：两边各自合代码时，若都从 1 开始挑，合并后必然撞号，而撞号不报错。
3. **接口头一列写文件名**（`disp.h`）就表示"这个服务有对外接口头"，门禁会验它真的存在、
   并且真的定义了表里那个号；写 `—` 表示服务存在但还没发布接口（与能力目录同样的写法）。

## 加一个服务时做什么

1. 在这张表里挑一个 `1–127` 的空号，补一行（名字 + 接口头 + 实现者）。
2. 在接口头里写 `#define <前缀>_SVC_ID <n>u`，四段注释里说明"没注册时调用方该拿什么码"。
3. `python3 tools/check_svc_ids.py` 应当 PASS；`./build.sh run` 一并验。
