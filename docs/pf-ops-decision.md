# pf_ops 九项裁决单（步骤 1.1）

> 本文只定**语义**，不定签名。签名在 1.2 落进 `platform/port/pf_ops.h`；两者冲突时以头文件为准，并回来改本文。
>
> 定稿日期：2026-11-02 · 状态：**已裁决，无待定项**

---

## 0. 先说范围：这张表是什么，不是什么

`pf_ops_t` 是平台必须提供的**基础设施**，只有九项。它不是"这台机器能干的所有事"。

| | 谁提供 | 有没有 | 缺失时 |
|---|---|---|---|
| **端口九项**（本文） | 每块板都必须实现 | 编译期就有 | 缺失 = 平台违约，`fw_init` 拒绝启动 |
| **能力位** `caps()` | 每块板如实汇报 | 运行期才知道 | 缺失 = `CM_ERR_NOT_SUPPORTED`，合法状态 |
| **服务**（显示/输入/音频/存储/网络/电源） | 服务 App，走注册表 | 运行期注册 | 未注册 = `CM_ERR_NOT_SUPPORTED` |

三句话版本：

- **端口九项是"一定有的机制"**——内存、时钟、睡眠、互斥、建任务、退任务。没有它们框架自己都跑不起来。
- **能力位是"这块板有没有这个硬件"**——`PF_CAP_DISPLAY` 可以是 1 而 `api/af_api/disp.h` 不存在（查得到硬件 ≠ 有接口可调）。
- **服务是"谁实现了这个驱动"**——注册表里没有，就是这块板没这功能。

九项之外的东西（显示、触摸、按键、存储、网络、音频、RTC、资源配额、事件）**一律不进这张表**。理由：端口表一旦长大，每接一块新板都要实现一堆它根本用不到的东西；而"用不到"和"没实现"就分不清了。

## 1. 裁决一：`pf_rtos.h` 与 `pf_ops.h` —— **合并成一张表**

结论：**只有一个头**，`platform/port/pf_ops.h`，`pf_rtos.h` 不再存在。

理由（三条，按重要性排）：

1. **它们是同一个接缝。** `pf_rtos.h` 原本要装的就是"时钟、睡眠、互斥、建任务"——和 `pf_ops_t` 里那五项完全重合。两个头装同一批函数，接板的人一定会问"我该实现哪一份"，答案是两份都得对，然后就开始漂移。
2. **前车之鉴。** `api/fp_api/` 就是这么死的：文档写"暂不使用"，而 `policy.txt`、`roles.md`、`coding-style.md` 三处继续引用它。**同一个东西有两个家，第二个家一定先烂。**
3. **接板的人只看一个文件就够。** 这是"换一块板不需要读懂框架"的物理前提：一个头、一张表、九项、每项一段注释。

被合并掉的 `pf_rtos.h` 唯一独特的内容是"这些是 RTOS 原语"，这一点由**注释与分节**表达（内存 / 时间 / 互斥 / 任务四节），不需要第二个文件。

## 2. 裁决二：`version` 与 `caps` 也是成员，但不计入"九项"

```c
typedef struct pf_ops {
    uint32_t version;     /* 必须 == PF_OPS_VERSION；否则 fw_init 拒绝启动 */
    uint32_t (*caps)(void);
    /* ... 九项 ... */
} pf_ops_t;
```

- `version` 是**结构体布局的版本**，不是板子的固件版本。框架用它判断"你填的表和我认识的表是不是同一张"。不匹配 → `CM_ERR_VERSION`，**不尝试兼容**（兼容旧表等于把两套语义永远养着）。
- `caps()` **是函数不是字段**：能力位必须在运行期可见（同一份固件可能烧到不同配置的板子上）。同理它不能是编译期常量。
- 九项 = 下面第 3–11 节的九条。**"九项"这个数字是契约的一部分**：`sizeof(pf_ops_t)` 变了，`version` 必须跟着变。

## 3. `void *mem_alloc(size_t bytes)`

| 五问 | 答案 |
|---|---|
| 入参边界 | `bytes > 0`。`bytes == 0` → 返回 `NULL`（不接受 0 字节分配，避免各平台返回 `NULL` 或不返回 `NULL` 的分歧） |
| 返回值 / 失败码 | 成功 = 可用指针（至少 `bytes` 字节、按 `max_align_t` 对齐）；失败 = `NULL`。**没有错误码**，`NULL` 是唯一失败信号 |
| 阻塞还是立即 | **立即返回**。分配器内部允许短暂加锁，但不允许等待"别的任务释放内存" |
| 中断可用 | **否**。ISR 里不许调；ISR 要用内存，只能由框架预先分配 |
| 非法 / NULL 参数 | 无 NULL 参数。超大 `bytes`（超过平台堆）→ `NULL`，不许崩溃、不许静默截断 |

补充约束：

- 这块内存**会被长期持有**（App 的 ctx、框架的注册表）。v1 **不提供 `realloc`**：没有它，App 只能"一次算准"或"申请新的+拷贝+释放旧的"——这两种写法都可审；有了 `realloc`，指针在重分配后失效这件事会静默发生。
- 归属与释放责任在调用方；框架的 `res_acquire` 会在此之上加登记（6.x）。

## 4. `void mem_free(void *p)`

| 五问 | 答案 |
|---|---|
| 入参边界 | `p` 必须是 `mem_alloc` 返回的指针，或 `NULL` |
| 返回值 | 无 |
| 阻塞还是立即 | 立即返回 |
| 中断可用 | **否** |
| 非法 / NULL 参数 | `mem_free(NULL)` **必须无操作**（合法）。**重复释放、释放非本分配器的指针 = 平台行为未定义**——框架不检查，靠测试与评审；host-fake 实现会**主动断言**（debug 构建下直接 abort），让错误在测试里暴露而不是在真机上偶发 |

## 5. `uint32_t clock_ms(void)`

| 五问 | 答案 |
|---|---|
| 入参边界 | 无 |
| 返回值 | **单调不减**的毫秒计数，从平台启动起算；回绕是正常的（`uint32_t` 约 49.7 天） |
| 阻塞还是立即 | 立即返回，**不允许阻塞、不允许加锁** |
| 中断可用 | **可以**——九项里**唯一**允许在 ISR 调用的 |
| 非法参数 | 无 |

用法约束（写进头文件注释，否则一定有人拿它当绝对时间）：

- 只能用于**间隔与超时**，不能当墙上时间。
- 比较必须写成差值：`(uint32_t)(clock_ms() - start) >= timeout`。直接比大小 `now >= start + timeout` 在回绕点上是错的。
- 精度要求：**±10% 或 ±1 tick（取大者）**。框架的所有超时都按"至少等这么久"设计，不依赖亚毫秒精度。

## 6. `void sleep_ms(uint32_t ms)`

| 五问 | 答案 |
|---|---|
| 入参边界 | `ms == 0` → **让出 CPU 一次**（不保证让给谁），不保证睡满 0ms 之外的东西 |
| 返回值 | 无 |
| 阻塞还是立即 | **阻塞调用者**，至少 `ms` 毫秒（允许更长，不允许更短） |
| 中断可用 | **否**（ISR 里睡眠是致命错误） |
| 非法参数 | 超大值（如 `UINT32_MAX`）→ 允许睡很久，框架不会传这么大的值；平台不必特判 |

关键约束：**`sleep_ms` 必须真的让出 CPU**。如果平台把它实现成忙等，"伪阻塞"整条机制就失效了——App 的 `fw_delay_block()` 会变成空转，看门狗会误报。这一条进 1.4 的契约用例。

## 7. `pf_mutex_t mutex_create(void)`

| 五问 | 答案 |
|---|---|
| 入参边界 | 无 |
| 返回值 | 成功 = 不透明句柄；失败 = `NULL` |
| 阻塞还是立即 | 立即返回（只在 boot 期调用，不走热路径） |
| 中断可用 | **否** |
| 失败怎么办 | 见下 |

- `NULL` 是**平台违约**，不是"这块板不支持锁"：框架的注册表表本身就要锁，没有锁就没有框架。`fw_init` 见到 `NULL` → `CM_ERR_INVALID`，拒绝启动，宁可不跑也不要跑一个会静默丢事件的框架。
- **不做 `mutex_destroy`**：v1 没有动态卸载 App，锁的生命周期 = 整个平台生命周期。少一个入口，就少一类"释放后又被 take"的 bug。真需要回收时，是重启整机。
- 递归性：**非递归**。同一任务重复 take 会自己把自己锁死；框架保证不这么写，`mutex_take` 不检查持有者（检查要额外存 owner，会把平台表拖胖）。

## 8. `int mutex_take(pf_mutex_t m, uint32_t timeout_ms)`

| 五问 | 答案 |
|---|---|
| 入参边界 | `m` 必须来自 `mutex_create`；`timeout_ms == 0` = **只试一次不阻塞** |
| 返回值 | `0` = 拿到；`-1` = 没拿到（超时）；其它非 0 值保留给平台错误（框架一律按"没拿到"处理） |
| 阻塞还是立即 | `timeout_ms == 0` 立即返回；否则**至多阻塞 `timeout_ms`** |
| 中断可用 | **否** |
| 非法参数 | `m == NULL` → 返回 `-1`（不崩溃）；框架不会传 NULL，但契约写明 |

**超时是相对语义**（这是最容易写错的一条）：从**调用那一刻**起算最多等 `timeout_ms`。写成"绝对截止时间"的实现，在传入 `clock_ms()` 时会立刻超时——1.4 里专门有一条用例抓它（睡 10ms 后 take 5ms 必须失败，而不是等 15ms）。

阻塞期间必须真正等待（让出 CPU），不许忙等；理由同 `sleep_ms`。

## 9. `void mutex_give(pf_mutex_t m)`

| 五问 | 答案 |
|---|---|
| 入参边界 | `m` 必须是当前任务持有的锁 |
| 返回值 | 无 |
| 阻塞还是立即 | 立即返回 |
| 中断可用 | **否**（ISR 里释放普通互斥是错的；ISR 与任务之间要用框架的 `fw_event_post_isr`，不用锁） |
| 非法参数 | 非持有者释放 = **未定义**，平台不检查；`m == NULL` → 无操作 |

## 10. `pf_task_t task_create(const pf_task_desc_t *desc)`

描述体只有四件事，**没有优先级**：

```c
typedef struct pf_task_desc {
    const char *name;              /* 只用于诊断，可被截断，框架不依赖内容 */
    void (*entry)(void *arg);
    void *arg;
    uint32_t stack_bytes;          /* 平台按自己的对齐要求向上取整 */
} pf_task_desc_t;
```

| 五问 | 答案 |
|---|---|
| 入参边界 | `desc`、`desc->entry` 非 NULL；`stack_bytes >= PF_TASK_MIN_STACK`（1024） |
| 返回值 | 成功 = 不透明句柄（框架不拿它做除了"记住"之外的事）；失败 = `NULL`（栈不够、任务数满了） |
| 阻塞还是立即 | 立即返回；新任务**可能已经开始跑**，调用方不能假设"返回时它还没动" |
| 中断可用 | **否** |
| 非法参数 | `desc == NULL` 或 `entry == NULL` → `NULL`；`stack_bytes` 太小 → `NULL`，**不许自动截断到最小栈** |

三条硬要求（进 1.4 契约用例）：

1. **优先级由平台自己定，描述体里没有**——框架不设优先级分带，也不允许 App 影响调度顺序。平台只要保证"所有任务都能被抢占"，否则 App 的 `fw_delay_block()` 会让整机饿死。
2. **栈由平台分配、由平台回收**（任务退出时）。框架不替任务管栈。
3. `entry` 返回即等于任务结束——平台必须把返回当作 `task_exit_current()`。

## 11. `void task_exit_current(void)`

| 五问 | 答案 |
|---|---|
| 入参边界 | 无 |
| 返回值 | **不返回**。这是契约里最硬的一条 |
| 阻塞还是立即 | 不返回，所以既不是阻塞也不是立即 |
| 中断可用 | **否** |
| 非法参数 | 无 |

为什么要单独占一项：框架的退出路径最后一步是"结束 App 任务"，而平台的任务 API 各家长得不一样（`vTaskDelete(NULL)` / `pthread_exit` / 直接 return）。把它做成**一项显式契约**，框架就不用 include 任何 RTOS 头——这是"框架不认识 RTOS"的实现方式。

配套约束：

- 实现里必须真的不返回。C 编译器不知道指针不返回，所以**框架不得在调用点之后放清理代码**——清理只能写在 App 的 `exit()` 回调里（伪阻塞机制的第 2 步）。
- 从任务外调用（主任务里）是未定义的；框架只在 App 任务里调。

## 12. 汇总：NULL 成员意味着什么

| 成员 | 为 NULL 时 |
|---|---|
| `version` / `caps` / 九项中任一项 | `fw_init` 返回 `CM_ERR_INVALID`，**拒绝启动** |

没有"可选成员"。理由：一旦允许某些成员为空，框架里每一处调用都要写 `if (ops->x)`，而这些分支在真机上一辈子只走一条——得不到测试的分支就是没有的分支。能力差异用 `caps()` 与服务注册表表达，不用"表里缺一格"表达。

（`caps()` 返回 0 是合法的：一块什么都没有的板子，能跑框架、能跑不依赖硬件的 App。）

## 13. 被否决的替代方案（记理由，别再翻）

| 方案 | 否决理由 |
|---|---|
| 保留 `pf_rtos.h` 单独一份 | 同一接缝两个家，见 §1；且强制接板人读两个文件 |
| 把 `sleep_ms`/`clock_ms` 换成"tick" | tick 频率是平台细节，App 与框架都按毫秒说话；暴露 tick 等于把 `configTICK_RATE_HZ` 泄漏进 App |
| 提供 `mutex_destroy` / `realloc` / `task_delete` | v1 无动态卸载，多一个入口多一类 use-after-free；需要时用重启整机（决定 8.x 的兜底策略同一口径） |
| 描述体里带优先级 | 框架不设优先级分带（architecture §3.5）；带上就一定会有人调它，调度顺序变成 App 的隐式契约 |
| 用宏开关做"可选能力" | 编译期开关会让 host 与真机跑不同的代码路径；能力必须运行期可见（`caps()`） |
| 九项里放"事件队列" | 事件是框架机制（`fw_event_post`），平台只提供"唤醒"；把队列放进端口表等于让每块板重新实现一遍队列语义 |

## 14. 1.2 要落的东西（本单的直接产物）

1. `platform/port/pf_ops.h`：`PF_OPS_VERSION 1`、`pf_mutex_t` / `pf_task_t` 不透明类型、`pf_task_desc_t`、`pf_ops_t`、能力位 `PF_CAP_*`（DISPLAY=0 … RTC=8，9–31 保留必须读 0）、`PF_TASK_MIN_STACK`。
2. 每个成员上方一段四段中文注释：入参（含边界）/ 返回（含失败码与输出参数状态）/ 线程与中断可用性 / 注意事项。
3. 头必须自包含：只允许 `<stdint.h>` / `<stddef.h>`，不 include 任何 `platform/` 以外的东西，也**不 include `common/`**。所以 1.2 **不写 `cm_types.h`**：端口表用 `int` / `NULL` 表达结果，错误码是框架内部把"平台失败"翻译成 `cm_err_t` 时才需要的。`common/include/cm_types.h` 推迟到第一次有框架代码要用它时（2.x），避免"先写类型再找用处"。
4. `pf_ops.h` 里只出现平台自己的东西：`PF_OPS_VERSION`、不透明类型、`pf_task_desc_t`、能力位、`PF_TASK_MIN_STACK`。任何 `cm_` 前缀出现在这个头里，都说明它把公共层拖进端口了。
