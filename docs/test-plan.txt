## 对应 md §1：硬约定的落地情况

- 第 1 条（零依赖）**已落地**：`tests/tinytest.h`、`tests/tinytest.py`、`tests/test.py`
  都是自己写的，无第三方依赖。
- 第 2 条（进程隔离 + 超时）**已落地**：`test.py` 里 `TIMEOUT_S = 20`，每个程序单独起进程。
  注意：这个环境**禁止给子进程建管道**（`_winapi.CreatePipe` → `PermissionError`），
  所以 `test.py` 与 `tinytest.py` 都是把输出重定向到临时文件再读回。
  **别改成 `capture_output=True`**，会直接报 PermissionError。
- 第 3 条（四种输出行）**已落地**：`tinytest.h` 与 `tinytest.py` 都按契约打印。
  解析器在 `test.py`：没有 `PASS/FAIL/SKIP` 行的程序判 `FAIL`。
- 第 4 条（同一份套件跑两处）**只有约定，还没有代码**：`tests/port/pf_conformance.c`
  不存在，`platform/port/pf_ops.h` 也不存在——九项的真实签名还没定（见
  `docs/code-structure.txt`）。

## 对应 md §6：夹具（这一块全没写）

`tests/support/` 需要两个文件，都还没写：

1. **`pf_fake_ops.c`** —— 一份 `pf_ops_t` 桩：
   - `clock_ms()` 返回测试控制的虚拟时间（全局变量 + `advance(n)`）
   - `sleep_ms(n)` 立即返回并把虚拟时钟推 `n`
   - `mem_alloc`/`mem_free` 用真 `malloc`（或可控失败的版本，用来测 `CM_ERR_NOMEM`）
   - 其余项填 NULL，用"该能力不支持"的路径跑降级分支
2. **`pf_fake_rtos.c`** —— 一份 `pf_rtos_t` 桩（18 个成员）：
   - `delay_ms` 推进虚拟时钟；`delay_accurate_us` 同
   - `task_create` 只记录任务体指针与名字，**不真起线程**（生命周期状态机可以单线程驱动）
   - `mutex_*`/`sem_*`/`queue_*` 用最小实现（能测"给了/没给"，不测真并发）

**为什么现在不写**：这两个文件要照 `pf_ops_t`/`pf_rtos_t` 的真实签名填，而
`platform/port/pf_ops.h` 与 `pf_rtos.h` 还不存在。九项与 18 个成员的名字在文档里，
但函数签名（参数类型、返回值）只是散文描述——照想象的签名写，等于把猜想固化成代码。

## 对应 md §7：`REQUIRES` 已落地

`test.py` 的 `REQ_RE` 解析文件头（前 4 KB）的 `// REQUIRES: <路径>` 与
`# REQUIRES: <路径>`，一行一个，可写多行。依赖不存在 → 整个程序判 `SKIP`。
`tests/tools/test_gates.py` 没写 `REQUIRES`，因为它只依赖 `tools/` 与 `policy.txt`，都真的在。

## 六条 v1 验收还没写成 `.c`

`docs/app-model.md` §7 的六条验收，用例名已经定死（**不要改名**，改名等于换了验收标准）：

| 用例名 | 断言什么 |
|---|---|
| `lifecycle_stop_latency` | 卡在 `fw_delay_block(200)` 的 App，置取消位到 `STOPPED` < 500ms（虚拟时钟） |
| `lifecycle_exit_once` | `exit()` 恰好一次；重启后变 2 |
| `lifecycle_restart` | `STOPPED` 后能再启动，回到 `RUNNING` |
| `lifecycle_illegal_transition` | 对非运行态调 `fw_app_stop()` → `CM_ERR_STATE` |
| `lifecycle_system_stoppable` | 带 `APP_FLAG_SYSTEM` 的 App 也能被停 |
| `lifecycle_init_fail_exits` | `init` 返回错误 → 仍调一次 `exit()`，状态 `FAILED` |

**为什么还写不出来**：这六条要 `framework/include/fw_app.h`（`fw_init`/`fw_boot`/
`fw_app_start`/`fw_app_stop`/`fw_app_state_of`）、`api/af_api/app.h`（`app_desc_t`）和
上面那两个夹具。三者都没有。硬写只能靠猜签名，猜错了要么编不过、要么更糟——编过了
但测的不是真东西。

**顺序**：先定 `pf_ops_t`/`pf_rtos_t` 与 `fw_app.h` 的签名 → 写夹具 →
再写这六条。写的时候放 `tests/sys/test_lifecycle.c`（整体系统测试），
不是 `tests/app/`。

## 还没定的小问题（等人裁决）

1. **`tests/api/` 与 `tests/common/` 归哪个 tag 写？** `policy.txt` v1.5 的
   `role 5 … tests/` 写了整个 `tests/`，所以现在 tag 5 能写全部测试。
   要不要像 `docs/` 那样按 tag 分子目录（`tests/app/`→2、`tests/sys/`→1 …）？
   子目录现在已经按层分了，但**没有对应的 `role` 行**——写错了也不会红。
2. **`cc` 不在 PATH 时怎么办？** 现在 `test.py` 依次找 `$CC` / `cc` / `gcc` / `clang` / `cl`，
   全找不到才返回 `2`。这台机器上只有 `clang`（`/c/Program Files/LLVM/bin/clang`），
   所以"找不到 `cc`"在 Windows 上是常态，不该报错。
3. **`tests/baseline/` 做什么还没有定义**。只在 `docs/code-structure.md` 的树里出现过，
   没人说它存什么快照、怎么比。
4. **真机怎么跑套件**（把哪一个 `.c` 编进哪个工程的哪个位置）没有写；等
   `platform/<板>/` 出现之后再定。
