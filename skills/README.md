# skills/ —— 按角色组织的工作说明

**这份目录回答**：你以哪个角色工作、能碰哪些文件、必须守哪些硬约束、停下时交什么、交付成什么格式。

| 角色 | 是谁 | tag | skill | 主用途 |
|---|---|---|---|---|
| **A** | 应用层 · 系统 App 作者 | 1 `sysapp` | [role-framework/SKILL.md](role-framework/SKILL.md) | 管理器（id 1）与各能力服务宿主 |
| **B** | 应用层 · 业务 App 作者 | 2 `aiapp` | [role-app/SKILL.md](role-app/SKILL.md) | **对外用途①：写 App** |
| **B** | 框架层作者 | 3 `framework` | [role-framework/SKILL.md](role-framework/SKILL.md) | 机制：生命周期、注册表、事件、伪阻塞 |
| **C** | 平台层作者 | 4 `platform` | [role-platform/SKILL.md](role-platform/SKILL.md) | **对外用途②：把一块板接进来** |
| **D** | 接口层作者 | 5 `api` | [role-api/SKILL.md](role-api/SKILL.md) | 定义 `api/`、`common/`、契约头、门禁、文档 |

> 目录名与 frontmatter 的 `name` 必须是 **kebab-case**（`role-app` 而不是 `role_app`）——这是宿主加载 skill 的要求，两者要一致。

## 三个前提

**① tag 是架构分层，不是人。** 一个人可以持多个 tag（"角色 B"同时持 2 和 3）；同一层可以有多个人。把 tag 当"用户名"，在第二块板、第二个 AI 出现时就会撞。`policy.txt` 只认 tag，角色字母只是习惯叫法。

**② 两个对外用途，不是一主一辅。** 让 AI 只写 `apps/` 就能在 ESP32 上跑，与让人只写 `platform/<板>/` 就能把板子接进来，**两者都要走通**。只有 App 侧顺、平台侧得先读懂框架源码，这套东西就退化成"只有原作者能移植"。

**③ 身份 ≠ 权限。** "我以平台开发者身份工作"不等于"拥有该角色的全部写权限"——写权限只看 `policy.txt`。`policy.txt`、构建文件、`.github/`、`AGENTS.md` 谁都不能写（只有人能改）。

## 为什么按角色拆，而不是一份总说明

- **约束不同。** 业务 App 作者不能碰框架，平台作者不能碰契约，接口层能改契约但不能改任何实现。合成一份，每条都要加"除某某角色外"，读的人反而不知道该守哪几条。
- **上下文成本。** 业务 App 作者只需要知道自己能 include 哪两个目录；把平台移植的验收顺序塞给他，是纯噪声。
- **触发不同。** `description` 是检索条件——"写 App"和"移植新板"是两件永远不该互相命中对方的事。

## skill 是什么

一个目录 + 一个 `SKILL.md`，开头是 YAML frontmatter：

```markdown
---
name: role-app
description: 什么时候该读这一份（触发指纹：写清"何时"和"做什么"）
---
```

`description` 不是简介，是**检索条件**。写"关于 App 的一些说明"永远匹配不上。

## 每份 skill 必须有的三节

1. **动手前的两道门** —— ①**改任何文件前先交清单，发出去后停下来等人说"可以"**（清单四项：完整路径 / 每处属于哪个 tag / 为什么不能只改现有的 / 大概多少行）。**用户点名"实现 X"不等于批准**，且不许自我豁免（"我判断这属于已批准范围""这是个小改""我先写完再交清单"）。不需要门的只有只读调查、跑命令看现象、回答问题和写清单本身。②**只有用户要求"出设计方案"时才写方案文档**，且先提交申请（写哪个路径、覆盖哪些改动）再落盘，写完交用户审批；用户没提方案就不要自己产文档。要写时落到**自己身份对应的 `docs/` 子目录**（`docs/sys/`、`docs/app/`、`docs/framework/`、`docs/platform/`，接口层用 `docs/` 根）。这一节要放在文件前部，不能塞在末尾。
2. **你能碰什么** —— 权限表 + `policy.txt` 对应行 + 自检命令。没有这一节，AI 只能靠猜。
3. **触发边界：命中任一条，立刻停** —— 该角色的停止条件、停下时交什么、不要做什么。

第 1 与第 3 两节是硬要求，其余各节讲"怎么做"，只有这两节约束"动手前先报备"和"什么时候不许做"。缺了它们，AI 会把"没被禁止"当成"被允许"，而且是**先改完再解释**——那时候代价已经付了。

## 谁能写

**最终只有人。** AI 能改 skill 就能删掉对自己不利的约束，然后依据改过的 skill 证明自己合规。

`skills/` 本身**只有人能写**：`policy.txt` v1.5 起已把它从 `role 5` 的写区摘掉（在那之前接口层能改，实测后果是 AI 把三份 skill 列进了自己的改动清单）。**AI 发现 skill 与实际不符 → 报告，不要自己改**；改约束必须走评审。`tools/` 仍暂时归接口层，收紧条件是"门禁稳定"。

## 待补

- 新增一份 skill 时，**必须同时加一行路由**（`AGENTS.md` 的文档地图 / 本表），否则进了仓库也没人读得到。
- 各 skill 里的自检命令分两类：`tools/` 的门禁脚本与 `tests/test.py` 的测试入口。**两类都已实现**（`python tools/validate.py` 当前 PASS；`tests/tools/test_gates.py` 12 条全绿），但门禁里有 6 步是 `SKIP`——因为 `api/`、`framework/`、`platform/`、`apps/` 还都是空的，没东西可查。**`SKIP` 不是通过**，交付时要写清楚哪一步跳过了、为什么。
- 测试要求不是可选项：每份 skill 都写明"改哪层的代码就补 `tests/<层>/` 的测试"，完整规则在 `docs/test-plan.md`，缺口在 `docs/test-plan.txt`。**改测试入口或 `LINK` 表等于改"测什么"，属契约变更，要评审。**
