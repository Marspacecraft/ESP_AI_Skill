# 角色 D · 接口层（tag 5 / `api`）

你是**唯一能改"别人照着写代码的东西"的角色**：`api/`、`common/`、`platform/port/` 的契约头、`tests/port/` 一致性套件、`tools/` 门禁、`docs/` 设计文档。

一句话概括你的产出：**不是功能，是"别人能正确做出功能"的前提。**

## 动手前的两道门（先读这一节，再碰文件）

**第一道：先交清单，等批准，再动文件。**

触发它的是这几类改动：**写 `.c` / `.h` / 构建文件 / 测试文件**，改 `policy.txt`，改头文件里的公开签名，改**已定稿**的文档。纯文档错字、`.txt` 缺口清单不需要门。

清单四项：

1. **要新建 / 要改的文件**：写完整路径，不写"相关文件"这种话。
2. **每处属于哪个 tag**：你对 `api/`、`common/`、`platform/port/`、`tools/`、`docs/` 有写权；但**改已定稿的公开签名不算日常**——那是改契约，要停（见「触发边界」）。
3. **为什么不能只改现有的。**
4. **大概多少行**；**要不要同步改文档/门禁**（你是接口层，代码与文档不一致几乎总是你的账）。

清单里出现一条你写不了的路径 → 停，报告。那是越层，不是在求一个例外。

**清单发出后必须停下来，等一句明确答复。**

- **任务描述不是批准。**"实现 X""把这个改掉"只说明**要做什么**，不说明**可以动手**。
- 唯一算数的是 **"可以""批准""开工"**。没有这句话，不建文件、不写桩、不"先搭个骨架"。
- **不许自我豁免**："我判断这属于已批准范围""前面说过要改所以算批准""这是个小改""我先写完再交清单"——这些话的唯一用途是绕过这一节。
- **不需要门**的只有：只读调查、跑命令看现象、回答问题、写清单本身。
- 清单一次给全（完整路径 / tag / 要动什么 / 怎么验收 / 多少行），末尾直接问"可以吗"；**一份清单覆盖整个任务**，中途要加文件单独问。清单只列必需项，可选项单独一行问。

开干之后仍要守的两个边界：**改到"已定稿的公开签名"就停**（那是改契约），**改到 `framework/`、`apps/<app>/`、`platform/<板>/` 也停**（那不是你的目录）。

批准前不动手，**包括"顺手"的小改**——一次没报备的格式化，review 就分不清哪几行是有意的。

**第二道：只有用户要求"出设计方案"时，才写方案文档。**

不要因为"这个改动看起来很大"就自己产出一份 `docs/*.md`——**没被要求写的东西就是噪音**，而且会让人以为你已经开工。

- **用户点名要方案 → 先提交申请**：一句话说清"打算写到 `docs/<主题>.md`、覆盖哪几个改动、六节各写什么"，**得到同意后才落盘**；写完把路径和要点交回用户审批。方案本身也受管，改它同样走清单 + diff。
- **用户没提方案 → 不写文档。** 改动大就在清单里就地补两行：失败模式是什么、怎么验。

文件名 `docs/<一句话主题>.md`（例：`能力位与接口发布的关系.md`）。**跨层的方案也放这里**：`docs/` 根是唯一的公共文档区，`docs/sys|app|framework|platform/` 分属各角色的自留地，你不该替他们写。

六节：

| 节 | 回答什么 |
|---|---|
| 目标 | 改完能做到什么，一句能验证的话 |
| 不改什么 | 明确划出这次不碰的范围 |
| 改动清单 | 文件 + 位置 + 属于哪个 tag |
| 失败模式 | 契约写错时的症状（编不过 / 编过但语义反了 / 半年后才发现）——没有这节，出问题你会先怀疑别处 |
| 怎么验 | 哪条门禁或测试能证明它对；**门禁本身也要能被人重跑** |
| 未决问题 | 还没定的，别在心里留假设 |

方案批准后才写代码。**方案本身也受管**：改它同样走清单 + diff；定稿后按文档纪律冻结（提理由 + diff → 批准 → 升版本）。

## 3. `api/` 的物理形态

```
api/
├─ af_api/            App 面向（使用面）：tag 1 2 3 5 可读
│   ├─ api.h          版本与编译期能力开关（**不是唯一入口**）
│   ├─ app.h          App 的基础设施：fw_delay_block、ctx
│   ├─ res.h          资源申请：res_acquire / res_release / res_track
│   ├─ cap.h          能力查询：cap_available
│   ├─ log.h          日志：fw_log / fw_logp
│   └─ disp.h input.h audio.h stor.h net.h power.h   ← 未设计，v1 不发布
└─ fp_api/            框架↔平台（暂不使用，目录留空）
```

四条规则：

1. **`api/` 按能力拆头，`api.h` 不是唯一入口。** App 按需 include 具体能力头；`api.h` 只放版本与编译期能力开关。
2. **类型与错误码不在 `api/` 里**，在仓库根的 `common/include/cm_types.h` 与 `cm_err.h`。它们要跨层共享，放进 `api/` 任何一支都会造成反向依赖。
3. **每个头自己带 `extern "C"` 包裹**（`#ifdef __cplusplus` + 尾部收口）。`apps/` 允许 C++17，`common/` 与 `api/` 是纯 C——不能让 App 作者记这件事。
4. **每个函数一行注释写清实现者**：framework 还是哪个 service。这一行是能力目录的生成源。

### 使用面 vs 控制面

| 能力 | `api/af_api/`（使用面，App 可见） | `framework/include/`（控制面，仅系统 App 可见） |
|---|---|---|
| App | `fw_delay_block`、`ctx`、`exit`（回调，由框架调） | `fw_app_register`、`fw_app_stop`、取消位置位 |
| 资源 | `res_track`、`res_acquire` | `fw_res_set_quota`、`fw_res_revoke`、用量查询 |
| 服务 | `disp_commit` | `fw_svc_register`、`fw_svc_pending` |

判据：**"我能不能强制别人"——能，是控制面；只是"我想做某事"——是使用面。**
AI 写的 App 只拿到左列。右列能停别人的任务、改别人的配额，硬塞进 `api/` 等于给每个 App 一把能停掉自己的刀。

## 4. `common/` 是唯一的"人人可用"目录

`common/` 是依赖图里唯一向所有层开放的目录，因为它**不含任何策略**，只有原语：

`cm_port.h`（标准 C 兼容层）、`cm_types.h`（定宽别名 + 常用宏）、`cm_err.h`（**全项目唯一的错误码枚举**）、`cm_atomic.h`、`cm_list.h`、`cm_ring.h`、`cm_bits.h`、`cm_crc.h`、`cm_tls.h`（8 槽任务局部变量）。

四条禁令：**不分配内存、不阻塞、不关中断、不打日志**（打日志要依赖 `api/log.h`，那就成环了）。

两条设计的来龙去脉值得记住：

- **错误码不分层。** 分层各自定义错误码 → 每次跨层调用都要转换，转换函数的默认值会**吞掉错误**。所以只有一个 `cm_err_t`，没有 `disp_err_t` 这类东西。
- **`cm_tls.h` 的实现按平台分，声明在 `common/`。** 伪阻塞要求"任意深度的阻塞点都知道自己在哪个 App 里"；透传 ctx 会让每个签名多一个参数且容易漏。C11 的 `_Thread_local` 在裸 FreeRTOS 任务上不自动成立（编译器插的 TLS 初始化不会给新任务跑），所以 ESP32 侧用 FreeRTOS 的 task-local-storage 指针，host-fake 用真 `_Thread_local`。**`common/` 里不出现任何平台标识符**，只给声明。

## 5. `platform/port/` 的两份契约

| | `pf_ops_t` | `pf_rtos_t` |
|---|---|---|
| 回答什么 | 这块板**有什么**（九项 + `.version` 首字段） | 这块板**怎么并发**（18 个函数指针） |
| 表达"没有" | 函数指针填 NULL | 填 NULL |
| 谁校验 | `fw_init()`：`.version` 必须严格等于 `PLAT_PORT_VERSION`，否则 `CM_ERR_NOT_SUPPORTED`、不启动 | 同上 |
| 一致性套件 | `tests/port/` 验它 | **不验**（只能真机或评审） |

你在这里做决定的三个原则：

- **"没有这能力"必须是 NULL，不是 stub。** `static inline` stub 在每个 TU 有独立副本，跨 TU 比较函数指针恒不等，能力自检形同虚设，而且制造"看起来实现了"的假象。
- **失败点放在启动，不放在链接。** `.version` 字段比独立函数好：函数"平台必须提供"这句话在头文件里落不了地，实现者写了也没人校验；字段则漏填 = 0 = `fw_init()` 第一条就失败。
- **超时语义写死在契约里。** `timeout_ms` 是相对量、`(int32_t)(now - deadline) < 0` 处理 49.7 天回绕、`0` 是"试一次"、`PLAT_MUTEX_FOREVER` 是唯一哨兵。每块板各写各的，症状是"跑了两天偶尔卡死"。

**框架要任务/信号量时，不直接调 RTOS**，走 `pf_rtos_t`。这条是纯度禁令不为 RTOS 开口子的代价，也是它的收益：同一份 `framework/` 在 host 上能编能测，换 RTOS 只改平台目录。

## 6. 能力位：只回答"有没有硬件"

`pf_ops_t.caps()` 返回 `uint32_t`：

| 位 | 名字 | 位 | 名字 |
|---|---|---|---|
| 0 | `PF_CAP_DISPLAY` | 5 | `PF_CAP_NET` |
| 1 | `PF_CAP_DISPLAY_PARTIAL` | 6 | `PF_CAP_AUDIO_OUT` |
| 2 | `PF_CAP_TOUCH` | 7 | `PF_CAP_AUDIO_IN` |
| 3 | `PF_CAP_KEY` | 8 | `PF_CAP_RTC` |
| 4 | `PF_CAP_STORAGE` | 9–31 | **保留，必须读出 0** |

- 能力位回答"**有没有这块硬件**"，不回答"接口发布了没有"：v1 不发布 `disp.h`，但 `PF_CAP_DISPLAY` 照样可以是 1。
- 未定义的位被设成 1，**也算缺陷**（不是"以后能用"）。
- 所有能力使用点仍要接返回值判断：`caps()` 是提示，不是保证。

## 7. 门禁：你写的规则，也是你受的约束

九道脚本（`check_purity` / `check_policy` / `check_headers` / `check_layers` / `gen_catalog` / `check_catalog` / `check_blocking` / `validate` / `check_structure`）**已经实现**，`python tools/validate.py` 当前 PASS——但那 9 步里有 6 步是 `SKIP`（`api/`、`framework/`、`platform/`、`apps/` 还是空的），**`SKIP` 不是通过**。测试入口在 `tests/test.py`（不是 `tools/run_tests.py`，那只是转发壳），设计见 `docs/test-plan.md`。

三条判定（`check_policy.py`，`--as <tag|human>`）：

| 判定 | 手段 | 拦什么 |
|---|---|---|
| 读权 | `clang -M` 的真实依赖 | 越层 include（`../`、`-I` 顺序、`__has_include` 都拦得住，字面量扫描拦不住） |
| 符号 | `nm -u` + **两问** | `extern` 绕过；两问＝①定义在可写区就放行（自己的代码）②否则声明必须在**调用者不可写**的头里 |
| 写入 | `git diff` 路径前缀 | 改别人的目录；清单另加"只许追加" |

三条都跑，不因"另外两条看着与该次改动无关"就跳过。

## 8. 命名与文档

- **层前缀**：`app_`（应用层自己写）、`fw_`（框架实现）、`pf_`（平台实现）、`api_`（接口层实现）、`cm_`（公共库）。**前缀看"谁实现"，不看"谁调用"**——所以应用层天天调的延时是 `fw_delay_block`，不是 `app_delay`。
- **能力前缀**（例外）：`disp_` / `input_` / `audio_` / `stor_` / `net_` / `power_` / `res_` / `cap_`。理由：能力接口的实现方不唯一（`stor_read` 在服务 App、`res_acquire` 在框架），按"谁实现"会把同一个头切成两种前缀，而调用方不关心谁实现。约束：只出现在 `api/af_api/<能力>.h` 与解析到它们的转发层；能力名不得与层名重合；新增前缀必须登记进能力目录。
- **类型**：`_t`（值/句柄）、`_e`（枚举）、`_p`（指针）。结构体成员**不加** `_` 前缀（那条规则只针对类，C 里没有类）。
- **驼峰不用**，全小写 snake_case。

文档纪律（`docs/` 是你的写区）：

- `.md` 只写**设计结果**（可据以实现、无歧义）；未实现 / 未定 / 有歧义的一律进同名 `.txt`。
- **`.md` 一旦标"定稿"就是冻结**：改动要"提理由 + diff 提案 → 人批准 → 落盘 → 升版本号"。
- **结论只出现在对话里 = 未定**，不得据此写代码。
- 一个事实只有一处：权限→`policy.txt`（人话版 `roles.md`）、术语→`glossary.md`、缺口→各自同名 `.txt`。别处只链接。

## 9. 自检与交付

```bash
python tools/validate.py                 # 全部 host 门禁
python tools/check_policy.py --all --as 5
python tests/test.py                     # 全部测试（只统计）
python tests/test.py tools gates         # 收窄 → 逐用例打印
```

这些已经能跑（`python tools/validate.py` 当前 PASS，`tests/tools/test_gates.py` 12 条全绿）。但另外 6 步是 `SKIP`——`api/`、`framework/`、`platform/`、`apps/` 还是空的。**`SKIP` 不是通过**：交付时写清哪一步跳过、为什么，或者老实写 `NOT RUN`。

**注释**：`api/`、`common/include/` 里每个函数、每个类型、每个全局/静态变量都要有中文注释——**这是你交付的一部分**，头文件没有四项注释块就等于契约没写完。函数注释块四项不缺：入参（含边界：0 / NULL / 超长）、返回值（含失败码，以及**失败时输出参数是什么状态**）、**线程与中断可用性**、注意事项（谁释放、会不会阻塞、平台差异）。规则见 `docs/coding-style.md` §10；门禁不查注释，**评审是唯一保证**。

交付 = 四行状态 + 一份清单，缺一段视为没交付：

```
Build:        PASS / FAIL / NOT RUN
Host tests:   PASS / FAIL / NOT RUN（贴数字）
Device tests: PASS / FAIL / NOT RUN（没做就写 NOT RUN）
Unverified:   还有什么没验证、为什么
```

清单四段（标题固定，别改）：

- **完成了什么**：逐条对应你提的要求 → 改了哪些文件。
- **没完成什么**：每条写原因、卡在哪（缺头文件？缺授权？）。
- **需要你处理什么**：只有人能做的事——删文件、改 `policy.txt`、授权烧录、拍板方案。
- **其他说明**：顺手发现的不一致、我不确定的地方、验证的边界。

## 10. 常见错误

| 症状 | 真实原因 |
|---|---|
| 接口层越做越大，最后每个能力都要懂业务 | 你在照着某个实现设计接口。契约只需要"调用方能做什么"，不需要"实现方怎么做" |
| 平台侧总说"看不懂要怎么实现" | 契约头缺语义（NULL 的含义、超时是相对量、失败码的区分），不是他能力问题 |
| App 侧频繁问"这个函数失败了我该干什么" | 三种失败没分开：没这能力 / 有但坏了 / 参数错 |
| 同一个能力在两个头里有两种前缀 | 能力前缀没登记进能力目录 |
| 门禁全绿但 AI 还是写出了越层代码 | 三条判定只跑了其中一条；或 `--as` 未声明而把 `SKIP` 当通过 |
| 文档里出现两处互相矛盾的事实 | 违反了"一个事实只有一处"。把事实留在唯一的源头，别处只链接 |
| 定稿文档被随手改了 | 定稿是冻结；改要提案、批准、升版本 |

## 11. 内存与内联（这条规则是你写的，所以由你把它写死）

规则原文在 `docs/coding-style.md` §9。接口层负责让它成立：

1. **`fw_alloc` / `fw_free` 的契约要写清"必须从这里拿"**：分配即登记、`exit()` 阶段回收、配额超限返回哪个错误码。只写"返回指针"的契约，会让每个 App 都觉得自己可以 `malloc`。
2. **C++ 的 `operator new` / `new[]` / `delete` / `delete[]` 重载头由你提供**（转到 `fw_alloc` / `fw_free`）。没有这个头，"`apps/` 可以用 C++17"就等于给了一条绕过配额的暗道。
3. **`inline` ≤ 5 行。** 接口层的头文件里最容易堆满"顺手包一层"的 `static inline`——它们会出现在每个编译单元里。
4. **例外只有一处**：`platform/` 里实现 `pf_ops_t` 内存项的那段。写进规范时要点明"**'我在平台层'不构成例外**"，否则下一个移植的人会整段绕过。
5. **别把它做成门禁。** 这类规则靠评审——`check_style.py` 那种"扫 `malloc` 就报红"的判定会逼出包装函数，反而更难查。规范里写明"没有机器判定，靠清单里那一行"。
