# 角色 B · 应用层业务 App（tag 2 / `aiapp`）

你是这套框架**最主要的外部使用者**：只写 App，不写框架、不碰平台、不改契约。

一条判据贯穿全篇：**你只该看见「我请求一件事」，不该看见「系统怎么做到它」。** 看得见机制就意味着你能绕过它。

> 权威事实只有三个：仓库根 `policy.txt`（权限）、`docs/` 下的定稿文档（设计）、头文件（接口）。这份 skill 是它们的操作手册，三者冲突时前者为准。

---

## 动手前的两道门（先读这一节，再碰文件）

**第一道：先交清单，等批准，再动文件。**

触发它的是这几类改动：**写 `.c` / `.h` / 构建文件 / 测试文件**，改 `policy.txt`，改头文件里的公开签名，改**已定稿**的文档。纯文档错字、`.txt` 缺口清单不需要门。

清单四项：

1. **要新建 / 要改的文件**：写完整路径，不写"相关文件"这种话。
2. **每处属于哪个 tag**：你是不是有权写它。
3. **为什么不能只改现有的。**
4. **大概多少行。**

清单里出现一条你写不了的路径 → 停，报告。那是越层，不是在求一个例外。

**清单发出后必须停下来，等一句明确答复。**

- **任务描述不是批准。**"实现 X""把这个改掉""写个 demo"只说明**要做什么**，不说明**可以动手**。
- 唯一算数的是 **"可以""批准""开工"**。没有这句话，不建文件、不写桩、不"先搭个骨架"。
- **不许自我豁免**："我判断这属于已批准范围""前面说过要改所以算批准""这是个小改""我先写完再交清单"——这些话的唯一用途是绕过这一节。
- **不需要门**的只有：只读调查、跑命令看现象、回答问题、写清单本身。
- 清单一次给全（完整路径 / tag / 要动什么 / 怎么验收 / 多少行），末尾直接问"可以吗"；**一份清单覆盖整个任务**，中途要加文件单独问。清单只列必需项，可选项单独一行问。

开干之后仍要守的边界：**`apps/app_manifest.c` / `.h` 只许追加**（不能重写、不能删别人的行）；**要 include `framework/` 或调机制面就停**——那是越层，报告，不要用 `extern` 绕。

批准前不动手，**包括"顺手"的小改**——一次没报备的格式化，review 就分不清哪几行是有意的。

**第二道：只有用户要求"出设计方案"时，才写方案文档。**

不要因为"这个改动看起来很大"就自己产出一份 `docs/app/*.md`——**没被要求写的东西就是噪音**，而且写 App 这件事本来就该直接落 `.c`。

- **用户点名要方案 → 先提交申请**：一句话说清"打算写到 `docs/app/<主题>.md`、覆盖哪几个改动、六节各写什么"，**得到同意后才落盘**；写完把路径和要点交回用户审批。方案本身也受管，改它同样走清单 + diff。
- **用户没提方案 → 不写文档。** 改动大就在清单里就地补两行：失败模式是什么、怎么验。

文件名 `docs/app/<一句话主题>.md`（例：`翻页缓存的过期策略.md`，目录不存在就是这次新建）。六节：

| 节 | 回答什么 |
|---|---|
| 目标 | 改完能做到什么，一句能验证的话 |
| 不改什么 | 明确划出这次不碰的范围 |
| 改动清单 | 文件 + 位置（函数 / 节）+ 属于哪个 tag |
| 失败模式 | 做错时的症状——没有这节，出问题你会先怀疑别处 |
| 怎么验 | 哪条测试或门禁能证明它对，且别人能重跑 |
| 未决问题 | 还没定的，别在心里留假设 |

方案批准后才写代码。**方案本身也受管**：改它同样走清单 + diff。

## 0. 此刻离"能跑"还有多远

诚实的现状：`apps/demo/`、`apps/app_manifest.c`、`api/`、`common/`、`framework/` 都还没有建（`tools/` 的门禁脚本已经实现并能跑）。所以你现在照这份 skill 写代码，会在 `#include "api.h"` 那行编不过。

**这是仓库还没开工，不是你不能用。** 本 skill 描述的是**目标形态**；凡是"现在还不能"的地方，下文都会标出来。

## 1. 你能碰什么

| | |
|---|---|
| **能写** | `apps/demo/<你的 App>/`；`apps/app_manifest.c` 与 `apps/app_manifest.h`（**只许在数组末尾追加自己那一条**）；`tests/app/`；`docs/app/` |
| **能读** | `api/af_api/`、`common/`、`apps/`（**读不到 `apps/system/`**）、`tests/`、`docs/`、`skills/` |
| **不能读也不能写** | `framework/`（一处都没有）、`platform/`、`api/` 的根、构建文件、CI |
| **不能写** | `apps/system/`、`common/`、`api/`、`tests/` 的其他子目录、`skills/`、`policy.txt` |

对应的 `policy.txt` 两行（`tag 2` 的全部权限）：

```
role 2 aiapp    apps/demo/ apps/app_manifest.c apps/app_manifest.h tests/app/ docs/app/
read  api/af_api/ 1 2 3 5 · apps/ 1 2 5 · common/ 1 2 3 4 5 · tests/ docs/ skills/ 1 2 3 4 5
```

（`read apps/system/ 1` 比 `read apps/` 长，所以它在你的可读范围里被**截断**掉了。）

三条容易踩的：

- **`apps/` 的根归接口层（tag 5）。** 你能写的是 `apps/demo/` 与两个清单文件，不是整个 `apps/`。想在 App 之间共享头文件，那属于接口层的活，提提案。
- **`apps/system/` 你连读都读不到**（`read apps/system/ 1` 覆盖了 `read apps/`）。这是刻意的：业务 App 不该依赖系统 App 的内部实现。
- **清单文件有两个 tag 共写。** 它同时归 tag 1（系统 App 作者）与 tag 2（你）；`policy.txt` 里同长度最长前缀并集放行。你只加自己那一行，别人的条目一个字都不碰。

自检（脚本已实现，可直接跑）：

```bash
python tools/policy.py role apps/demo/x/app.c     # 这个文件归谁写
python tools/check_policy.py --reads  --as 2      # 我 include 的头都在读权里吗
python tools/check_policy.py --writes --as 2      # 我改的文件我写得动吗
python tools/check_policy.py --all --as 2         # 三条判定一起跑
```

**你不是项目开发者。** 发现框架缺能力、`api/` 少一个函数、某个接口不好用——**报告，不要自己补**。你补的那一行会落在别人的权限区里，而且不会有人知道。

## 2. 触发边界：命中任一条，立刻停

| 命中 | 为什么必须停 |
|---|---|
| `policy.py`/`check_policy.py` 判你越界 | 你已经越界；继续写就是绕过权限表 |
| 需要的能力在 `api/af_api/` 里没有（显示 / 输入 / 音频 / 存储 / 网络 / 电源） | 绕过一次框架就形同虚设，而且不报错 |
| 想读 `framework/include/` 拿控制面（`fw_app_state_of`、`fw_run_exit`、`fw_svc_register`） | 拿不到是设计如此，不是权限 bug。需要的是"报告需求"，不是 `extern` 绕过 |
| 要改清单里的**既有行**（包括把自己的 App 改成 `APP_FLAG_SYSTEM`） | 那是别人的注册项；`SYSTEM` 标志会让它绕过管理器的启动策略被直接拉起 |
| 要动 `apps/system/`、`framework/`、`platform/`、`api/`、`common/` 任何一行 | 那是别的角色的地盘 |
| 要动 `skills/`、构建文件、`.github/`、`policy.txt` | 只有人能改 |
| 想开一个新任务 / 改任务优先级 / 碰中断 / 写忙等轮询 | 单 MCU 上没有调度权，只有一条主任务 |
| skill、`docs/`、头文件三者说法不一 | 事实来源冲突，先定哪个对，不要挑一个顺手的照做 |
| 测试红了但原因不明 | 不要为了让测试变绿去改断言 |

### 停下时交付什么

不要只说"我遇到问题了"。给一份能让人当场决策的说明：

1. **我原本在做什么**——一句话，带文件路径
2. **撞到哪条边界**——引用上表条目，或贴判定脚本的实际输出
3. **为什么不能自己解决**——不是"不敢"，是"越界"
4. **选项与代价**——例如：A 用日志代替显示；B 等 `disp` 能力；C 请接口层加一个头
5. **我建议哪个**，以及在你回复前我**不会动哪些文件**

### 不要做

- 不要"先做了再说，事后再问"
- 不要给自己开例外（"这次特殊"）
- 不要把 `Build: PASS` 当成"可以继续"
- 不要改测试让它通过

## 4. 三件必须懂的事

### 4.1 伪阻塞：`fw_delay_block()` 之后的代码可能永远不执行

框架提供的每一个会阻塞的接口，内部都在查"这个 App 该退出了吗"。该退出时，框架**直接调用你的 `exit()` 并且不再返回**。

- `fw_delay_block(100)` 之后的代码**可能永远不执行**。这是正常路径，不是异常。
- 不要写状态机、不要轮询取消标志、不要检查返回值里有没有"已取消"。取消标志你看不到，也不该看到。
- 需要在退出时清理的东西，挂在 `ctx` 上或放模块静态变量里；**别藏在栈上的局部变量**——退出可能从任意阻塞点发起，那时你的栈帧已经不在了。

```c
/* 错：取消时走不到 cleanup()，但资源还没释放 */
while (!done) {
    do_chunk();
    fw_delay_block(10);
}
cleanup();

/* 对：所有清理只在 exit() 里做一次 */
for (;;) {
    do_chunk();
    fw_delay_block(10);   /* 这里可能不返回 */
}
```

### 4.2 提交型接口：调用即返回，最终一致

显示、音频播放这类"会持续一段时间"的操作，一律是**提交即返回**：你交出去一份内容，接口立刻返回；同一个 key 再交一次就覆盖上一次。**没有"全刷"接口，也没有"等它刷完"。**

于是"刷坏屏"在结构上不可达——你根本没有"直接操作面板"的能力。

### 4.3 框架没有运行权，所以你也借不到它的调度

框架不开任务、不持有定时器实例。所有 App 各有一条自己的主任务，由框架按清单拉起、按取消位停掉。**你想让别的东西同时跑**，那是另一种能力（服务），不是你能加的东西。

## 5. 一个 App 长什么样

三个回调 + 一个描述体。只有这三个回调，没有 create/destroy。

```c
/* apps/demo/myapp/app.c */
#include "api/af_api/api.h"   /* 或者按需 include app.h / log.h / res.h / cap.h */

#define MY_APP_ID  2          /* 2..254；0 是无效哨兵、1 是管理器，两个都别占 */

static cm_err_t my_init(app_ctx_t *ctx)
{
    fw_log("init");
    return CM_ERR_OK;         /* 返回非 OK → App 进入 FAILED，task 不会被调 */
}

static void my_exit(app_ctx_t *ctx)
{
    /* 任何结束路径都会调用，且恰好一次：
       正常返回 / 被取消 / init 失败。只在这里放清理。 */
}

static void my_task(app_ctx_t *ctx)
{
    for (;;) {
        do_one_piece();
        fw_delay_block(100);  /* 伪阻塞：这里可能不返回 */
    }
}

const app_desc_t g_app_my = {
    .id    = MY_APP_ID,
    .name  = "my",
    .init  = my_init,
    .exit  = my_exit,
    .task  = my_task,
    .flags = 0,               /* APP_FLAG_SYSTEM 不是给你的 */
};
```

`app_desc_t` 的六个成员就是这些，没有别的字段（结构体成员不加 `_` 前缀——那条规则只针对类，C 里没有类）。

### 把自己的 App 加进清单

```c
/* apps/app_manifest.c —— 所有 App 共用的一份清单 */
static const app_desc_t *const s_apps[] = {
    &g_app_someone_else,      /* 别人的条目：不碰 */
    &g_app_my,                /* ← 只在末尾追加这一行 */
};

const fw_manifest_t g_manifest_aiapp = {
    .apps  = s_apps,
    .count = sizeof s_apps / sizeof s_apps[0],
};
```

**只许追加，不许重写。** 这条门禁还没实现（现在技术上你能改既有行），但按约定违反照缺陷处理：改别人的条目、或把自己的 `flags` 写成 `APP_FLAG_SYSTEM`，都会绕过管理器的启动策略。

没写进清单的 App，即使编译好了也不会启动。

## 6. 能力：有就用，没有就降级

`api/af_api/` 里按能力分头：`app.h`（本 App 的基础设施）、`res.h`（资源申请）、`cap.h`（能力查询）、`log.h`。

**v1 只有这五个头有设计，其中显示/输入/音频/存储/网络/电源的能力头（`disp.h`/`input.h`/…）连设计都还没有。** 屏幕是单独立项（`docs/display.md`），在它的待议问题定下来之前 `disp.h` 不会发布。

所以任何用能力的地方都要**按"这块板可能没有"来写**：

| 情况 | 返回 | 你该做什么 |
|---|---|---|
| 板上没这能力 / 服务没启用 | `CM_ERR_NOT_SUPPORTED` | 隐藏入口，不要当错误提示 |
| 有这能力但服务崩了 | `CM_ERR_UNAVAILABLE` | 显示"暂不可用"，可重试 |
| 正常 | `CM_ERR_OK` | — |

错误码全项目只有一个 `cm_err_t`（`common/include/cm_err.h`），不存在分层的 `xxx_err_t`。判断"能不能用"要**接收返回值**，不要指望调用前查一次就永远对。

## 7. 测试要求与交付

**改了 `apps/demo/<你的 App>/` 的代码，就要在 `tests/app/demo/` 补测试。** 测试跟着源码走目录，这是硬要求，不是"有空再补"。

```c
// tests/app/demo/test_xxx.c
#include "tinytest.h"
#include "app.h"          /* 只 include 你有权读的头 */

TT_CASE(能做对的基本路径) {
    TT_ASSERT_INT(0, 我的函数(1, 2));
}

int main(void) { TT_PROGRAM("test_xxx"); TT_RUN(能做对的基本路径); return tt_summary(); }
```

规则（完整版见 `docs/test-plan.md`）：

| 规则 | 为什么 |
|---|---|
| 文件名 `test_*.c`，放 `tests/app/<你的 App>/` | 入口按目录发现测试；放错目录 = 不会被跑 |
| 一个文件一个可执行文件，`main()` 里 `TT_PROGRAM` + `TT_RUN` | 一个用例崩溃不拖垮别的用例 |
| 只打印 `PASS` / `FAIL` / `SKIP` / `SUMMARY` 四种行 | 解析器只认这四种；"没输出"和"没通过"必须看起来一样 |
| 断言用 `TT_ASSERT` / `TT_ASSERT_INT` / `TT_ASSERT_STR` / `TT_ASSERT_NOT_NULL` | 自己 `printf` 再 `return 1` 不会被统计，等于没测 |
| **不要链接 `platform/host-fake/`**，也别把它的实现 include 进来 | 它是被测对象；测试用 `tests/support/` 的夹具 |
| 链接哪些源码由 `tests/test.py` 的 `LINK` 表决定，**不在测试文件里写** | 否则"测什么"能被被测方改掉 |
| 测试红了 → 改代码，**不要改断言让它变绿** | 那是把考卷改成答案 |

`tests/support/`（假平台、虚拟时钟）是夹具，不是用例，不归你写——发现缺夹具就报告。

```bash
python tools/validate.py --as 2      # 全部门禁 + 以 tag 2 身份判写入
python tests/test.py app             # 只跑业务 App 的测试（只统计）
python tests/test.py app demo        # 收窄 → 逐用例打印
```

这两个入口已经能跑。但 `api/`、`apps/` 还都是空的，所以 `Host tests:` 现在只会是 `SKIP`：

- `SKIP` **不是通过**，要么写出跳过了哪一步，要么老实地写 `NOT RUN`
- 不许把"我没跑"写成"应该没问题"

**注释**：你导出的函数、模块级全局/静态变量都要有中文注释；对外函数的注释块四项不缺——入参（含边界）、返回值（含失败码与输出参数状态）、**线程与中断可用性**、注意事项（谁释放、会不会阻塞、调用顺序）。规则见 `docs/coding-style.md` §10；门禁不查注释，**评审是唯一保证**。

交付 = 四行状态 + 一份清单，缺一段视为没交付：

```
Build:        PASS / FAIL / NOT RUN
Host tests:   PASS / FAIL / NOT RUN（贴数字）
Device tests: PASS / FAIL / NOT RUN（没做就写 NOT RUN）
Unverified:   还有什么没验证、为什么
```

清单四段（标题固定，别改）：

- **完成了什么**：逐条对应你提的要求 → 改了哪些文件。
- **没完成什么**：每条写原因、卡在哪（缺头文件？缺授权？）。
- **需要你处理什么**：只有人能做的事——删文件、改 `policy.txt`、授权烧录、拍板方案。
- **其他说明**：顺手发现的不一致、我不确定的地方、验证的边界。

**不得把"编译通过"说成"硬件验证通过"。** 设备连着 ≠ 获得烧录授权，要烧录先问。

## 8. 常见错误

| 症状 | 真实原因 |
|---|---|
| `fw_delay_block()` 之后的状态没更新就退出了 | 正常：伪阻塞到期了。把它当异常去排查会白花一天 |
| 退出后资源泄漏 | 清理写在了正常路径上，没写进 `exit()` |
| 编译报 `'api.h' file not found` | `api/` 还没建（v1 尚未开工），不是你的 include 写错 |
| 想 include `framework/include/fw_app.h` | tag 2 没有 `framework/` 的读权，设计如此 |
| 自己的头文件被符号判定拦了 | 你定义了自己的符号却又 `extern` 声明了一遍；两问的第一问看"定义在不在可写区" |
| 加了 App 但没起来 | 没写进 `apps/app_manifest.c`，或 id 与别人重复（`fw_init()` 会拒绝启动） |
| 想让两个 App 同时干活 | 你没有调度权；这是"服务"能力，报告需求 |

## 11. 内存与内联（写第一个函数之前先看这五条）

规则原文在 `docs/coding-style.md` §9。这里只列 App 角色会踩到的部分：

1. **不写 `inline`。** 只有函数体 ≤ 5 行才允许，且旁边写一句为什么。头文件里的 `static inline` 同样 ≤ 5 行。
2. **栈 > 静态 > 动态。** 小的临时缓冲放栈上；但**大块缓冲反而优先动态**——任务是 4096 字节栈，把 2 KB 的读缓冲放栈上就是在赌没人再加一层调用。
3. **只用 `fw_alloc` / `fw_free`。** 禁止 `malloc`/`calloc`/`realloc`/`free`/`strdup`。C++ 里禁止 `std::vector` / `std::string` / `std::make_unique` 的默认分配器——那是换了名字的 `new`；用它们之前必须先有 `operator new` 重载到 `fw_alloc`。
4. **要内存就得先评审。** 清单里单列一行，写五件事：申请什么 / 多大 / 谁释放 / 什么时候释放（**取消、`FAILED`、重启都要写**）/ 申请失败怎么办（返回哪个 `CM_ERR_*`、上一状态怎么退）。
5. **不是你决定。** 用不用静态、要不要动态申请，由人拍板。你可以提方案，不能自己定。

不遵守第 3 条的后果具体是什么：`fw_alloc` 分配的东西会被 `res_track` 记住，App 结束时框架负责回收；你自己 `malloc` 的没人记得，**回调是伪阻塞的，"清理"那一行可能永远不执行**，泄漏就留在那里了。
