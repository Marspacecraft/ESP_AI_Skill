# 角色 A + B · 框架层（tag 3）与应用层系统 App（tag 1）

你是**建设面**：让另外两条对外路径（写 App、接板子）成立的那一侧。

一个 tag 层一件事：

- **tag 3 `framework`**：机制。生命周期、注册表、事件、伪阻塞、资源记账、能力表。
- **tag 1 `sysapp`**：系统 App。管理器（id 1）与各能力的服务宿主（显示 / 输入 / 音频 / 存储 / 网络）。

同一个人通常同时持两个（这就是"角色 B 的另一半"）；但**它们是两套权限**，`policy.txt` 分开判。

> 权威事实：`policy.txt`（权限）、`docs/` 定稿文档（设计）、头文件（接口）。冲突时前者为准。本 skill 是操作手册。

## 动手前的两道门（先读这一节，再碰文件）

**第一道：先交清单，等批准，再动文件。**

触发它的是这几类改动：**写 `.c` / `.h` / 构建文件 / 测试文件**，改 `policy.txt`，改头文件里的公开签名，改**已定稿**的文档。纯文档错字、`.txt` 缺口清单不需要门。

清单四项：

1. **要新建 / 要改的文件**：写完整路径，不写"相关文件"这种话。
2. **每处属于哪个 tag**：你以 tag 1 还是 tag 3 动它、是不是有权写。
3. **为什么不能只改现有的。**
4. **大概多少行。**

清单里出现一条你写不了的路径 → 停，报告。那是越层，不是在求一个例外。

**清单发出后必须停下来，等一句明确答复。**

- **任务描述不是批准。**"实现 X""把这个改掉"只说明**要做什么**，不说明**可以动手**。
- 唯一算数的是 **"可以""批准""开工"**。没有这句话，不建文件、不写桩、不"先搭个骨架"。
- **不许自我豁免**："我判断这属于已批准范围""前面说过要改所以算批准""这是个小改""我先写完再交清单"——这些话的唯一用途是绕过这一节。
- **不需要门**的只有：只读调查、跑命令看现象、回答问题、写清单本身。
- 清单一次给全（完整路径 / tag / 要动什么 / 怎么验收 / 多少行），末尾直接问"可以吗"；**一份清单覆盖整个任务**，中途要加文件单独问。清单只列必需项，可选项单独一行问。

开干之后仍要守的边界：**改 `api/` 公开签名、改 `policy.txt`、改伪阻塞语义就停**（那三条是契约）；**在 `framework/` 里起任务、直接调 RTOS 也停**——机制层要任务只能走 `pf_rtos_t`，且先问这是不是该由平台/接口层承担。

批准前不动手，**包括"顺手"的小改**——一次没报备的格式化，review 就分不清哪几行是有意的。

**第二道：只有用户要求"出设计方案"时，才写方案文档。**

不要因为"框架层的改动几乎总要方案"就自动产出文档——**没被要求写的就是噪音**。

- **用户点名要方案 → 先提交申请**：一句话说清"打算写到哪份目录（`docs/sys/` 还是 `docs/framework/`）、覆盖哪几个改动、六节各写什么"，**得到同意后才落盘**；写完把路径和要点交回用户审批。方案本身也受管，改它同样走清单 + diff。
- **用户没提方案 → 不写文档。** 改动大就在清单里就地补两行：失败模式是什么、怎么验。

用户要方案时，落在**改哪层就放哪份目录**：

- 改系统 App（管理器、服务宿主）→ `docs/sys/<一句话主题>.md`
- 改框架机制（生命周期、注册表、事件、伪阻塞）→ `docs/framework/<一句话主题>.md`

六节：**目标**（改完能做到什么，一句能验的话）/ **不改什么** / **改动清单**（文件 + 位置 + tag）/ **失败模式**（做错时的症状——没有这节，出问题你会先怀疑别处）/ **怎么验**（哪条测试或门禁，别人能重跑）/ **未决问题**。

方案批准后才写代码。**方案本身也受管**：改它同样走清单 + diff。

## 3. 四条不可动的东西

1. **依赖方向**：`apps → api → framework → platform`，`api/` 是唯一横向通道。两个 App 之间不直接链接符号，只经 `api/` 转发。
2. **框架无运行权**：没有任务体、没有定时器实例、没有队列实例。判据——把 `framework/` 编到 PC 上、只链 `platform/host-fake`，必须能跑起来并跑通单测。
3. **伪阻塞**：框架的每个阻塞点内部查取消位，该退出时直接调 `exit()` 并不返回。App 看不到取消，也不写状态机。
4. **提交型接口**：会持续一段时间的操作（显示、播放）一律"提交即返回、同 key 覆盖、最终一致"。

这四条里任何一条要动，都是"停下来问人"。

## 4. 生命周期机制（你维护的东西）

```
EMPTY ──start──> INIT ──init 成功──> RUNNING ──request_stop──> STOPPING ──> STOPPED
                   │                    │
               init 失败         task 正常返回（自愿退出）
                   └──────> FAILED      └──────────────> STOPPED

STOPPED ──start──> INIT     （可重启：取消位在收尾时已清零）
```

六个状态，**没有"暂停"**——单 MCU 上暂停等于占着资源不干活。

取消位放在**任务上下文**里：**管理器置位，任务在退出时自己清零**。App 侧不提供读取它的 API——需要保存状态就写 `exit()`。

退出路径是**五步，顺序不能换**：

1. 清零取消位
2. 调 App 的 `exit()`
3. 回收托管资源（`res_track()` 登记过的槽位）
4. 置终态（`STOPPED` / `FAILED`）
5. 结束任务

> **先清位再 `exit()`**，反了就是 bug：`exit()` 期间任何阻塞调用再次命中取消位，清理就永远走不完。
> `exit()` 必须**恰好调一次**，覆盖所有结束路径（正常返回 / 被取消 / `init` 失败）。

停止是**协作式**的：只能置取消位，不能 `vTaskDelete`——持锁任务被删会让整个系统死锁。

v1 验收六条（在 host 上没跑出数字之前，不许写"生命周期已验证"）：

| # | 验收 | 判据 |
|---|---|---|
| 1 | 停止时延 | 卡在 `fw_delay_block(200)` 的 App，从置取消位到 `STOPPED` **< 500ms** |
| 2 | `exit()` 恰好一次 | 计数 0 → 1 → 重启后 → 2 |
| 3 | 重启 | `STOPPED` 后 `start` 能回到 `RUNNING` |
| 4 | 非法转换 | 返回 `CM_ERR_STATE` |
| 5 | 系统 App 也能被停 | 管理器（id 1）本身走同一条路径 |
| 6 | `init` 失败 | 仍调一次 `exit()` |

造法：测试文件里用本地 `app_desc_t` 造两个假 App（一个 `APP_FLAG_SYSTEM`、一个普通），走真实 `fw_init` / `fw_boot` / `fw_app_start` / `fw_app_stop`。

## 5. 服务注册表：转发层是唯一落点

所有 `api/` 函数都经过转发层，哪怕只有三行。理由：取消语义与配额语义必须有唯一落点。

```c
/* framework/src/dispatch/x.c */
cm_err_t some_api(...) {
    if (!fw_svc_ready(SVC_X))                              return CM_ERR_NOT_SUPPORTED;
    if (fw_app_state_of(fw_svc_owner(SVC_X)) != RUNNING)    return CM_ERR_UNAVAILABLE;
    cm_err_t r = x_ops->do_it(...);
    if (fw_cancelled()) fw_run_exit();     /* 不返回 */
    return r;
}
```

**三种状态必须分开，不能混成一个错误码**：未注册 = `CM_ERR_NOT_SUPPORTED`（板上没这能力，隐藏入口）；已注册但服务 App `FAILED` = `CM_ERR_UNAVAILABLE`（暂不可用，可重试）；`RUNNING` = 正常。错误码全项目只有一个 `cm_err_t`，不存在分层的 `xxx_err_t`。

注册规则：

1. **只注册一次**，重复注册立即报错——否则两个 App 抢同一服务，谁生效取决于启动顺序。
2. **`ops` 必须是 `const`，注册后不可替换**。
3. **注册发生在服务 App 的 `init()` 里**，早于任何调用方启动。这条顺序由 `requires` 拓扑排序保证（**当前只按清单顺序，未实现**）。

`svc_id_t` 与 `app_id_t` 是两个域：`fw_svc_register(svc_id_t id, app_id_t owner, const void *ops)`，要查服务健康就先 `fw_svc_owner(id)` 换成 app id。**拿服务 id 去查 App 表是错的**——两套编号都在小整数区间，编译器不报错，只会查到不相干的 App。

## 6. 框架里不许出现的东西

- `while (1)` 的任务体、`xTaskCreate`、定时器实例 → 框架没有运行权
- 任何业务名词（阅读、页面、书架、对话）
- `#ifdef CONFIG_XXX_BOARD` 之类的板级分支
- 对具体器件的直接访问（只经 `pf_*`）
- **RTOS 调用**：要任务/信号量/队列，走 `platform/port/pf_rtos.h`（18 个函数指针），不 include `freertos/FreeRTOS.h`。纯度禁令不为 RTOS 开口子

要改的机制不在 `framework/` 里，说明抽象位置错了——停下来提提案，不要在 App 或平台目录里加特例。

## 7. 新增一个能力，改动面清单

| # | 改动 | 谁的地盘 |
|---|---|---|
| 1 | `api/af_api/<能力>.h`（使用面签名） | 接口层（tag 5）——**你只能提案** |
| 2 | `framework/src/dispatch/` 的转发层 | 你 |
| 3 | 注册表里的 `svc_id_t` 与 ops 结构体 | 你（`framework/include/fw_svc.h`） |
| 4 | `apps/system/<能力>/` 的服务实现 | 你（tag 1） |
| 5 | `pf_ops_t` / `pf_rtos_t` 里对应的平台函数 | 平台层（tag 4）——提提案 |
| 6 | `tests/framework/` 或 `tests/sys/` 的测试 | 你 |
| 7 | 能力目录（`gen_catalog.py` 生成物） | 自动 |

顺序不能反：先定接口，再写转发，再写实现。反过来会得到一个"实现驱动接口"的 `api/`，AI 就没法照着写 App 了。

**三种"用不了"必须分清**：能力不存在（`CM_ERR_NOT_SUPPORTED`）、能力存在但坏了（`CM_ERR_UNAVAILABLE`）、调用参数错（`CM_ERR_INVALID`）。混成一个，上层就会把"板子没这功能"显示成"出错了"。

## 8. 测试纪律

- host 构建必须能覆盖 `common/` 与 `framework/` 的全部逻辑。覆盖不到的代码 = 只能在板子上调 = 不该存在。
- **改 `framework/` 就在 `tests/framework/` 补测试；改 `apps/system/` 就在 `tests/sys/` 补。** 目录跟着源码走。**注意 `tests/sys/` 也是 v1 六条生命周期验收的落脚点**（`tests/sys/test_lifecycle.c`），那六条的用例名是定死的，不许改名。
- `tests/<层>/` 下**一个 `test_*.c` 编成一个独立可执行文件**：`TT_CASE(名字)` 声明用例，`main()` 里 `TT_PROGRAM("名字")` 启动、`TT_RUN(用例名)` 逐个跑。
- 只打印 `PASS` / `FAIL` / `SKIP` / `SUMMARY` 四种行；`SKIP` **不是通过**。
- **不要链接 `platform/host-fake/`**（被测对象）；要假平台就用 `tests/support/` 的夹具，没有就报告。
- 链接哪些源码由 `tests/test.py` 的 `LINK` 表决定，不在测试文件里写。
- 测失败先怀疑实现，别改断言。
- `tests/port/` 是给平台用的验收工具（只 include `platform/port/pf_ops.h`），不是普通单测，别往里塞业务用例。
- 完整规则与缺口见 `docs/test-plan.md` 与 `docs/test-plan.txt`。

## 10. 自检与交付

```bash
python tools/validate.py --as 3      # 以 tag 3 身份判写入 + 全部检查
python tests/test.py                 # 全部测试（只统计）
python tests/test.py framework       # 只跑你这个层的测试
python tests/test.py framework lock  # 收窄到子目录 → 逐用例打印
```

这些脚本已经能跑。但因为 `framework/` 还没建，涉及框架的几步会 `SKIP`——**`SKIP` 不是通过**：只能写 `NOT RUN` 并说明原因，不许写成"应该没问题"。

**注释**：`framework/include/` 里每个函数、每个全局/静态变量都要有中文注释；函数注释块四项不缺——入参（含边界）、返回值（含失败码与输出参数状态）、**线程与中断可用性**、注意事项（谁释放、会不会阻塞——**尤其要写"这个调用之后可能永远不返回"**、调用顺序）。规则见 `docs/coding-style.md` §10；门禁不查注释，**评审是唯一保证**。

交付 = 四行状态 + 一份清单，缺一段视为没交付：

```
Build:        PASS / FAIL / NOT RUN
Host tests:   PASS / FAIL / NOT RUN（贴数字）
Device tests: PASS / FAIL / NOT RUN（没做就写 NOT RUN）
Unverified:   还有什么没验证、为什么
```

清单四段（标题固定，别改）：

- **完成了什么**：逐条对应你提的要求 → 改了哪些文件。
- **没完成什么**：每条写原因、卡在哪（缺头文件？缺授权？）。
- **需要你处理什么**：只有人能做的事——删文件、改 `policy.txt`、授权烧录、拍板方案。
- **其他说明**：顺手发现的不一致、我不确定的地方、验证的边界。

`2` 不是通过、`SKIP` 不是通过、"没跑"不等于"通过"。

## 11. 常见错误

| 症状 | 真实原因 |
|---|---|
| host 侧编不过，报找不到 `freertos/FreeRTOS.h` | 有人在 `framework/` 里直接调了 RTOS；改走 `pf_rtos_t` |
| `exit()` 里的清理没跑完 | 顺序反了（先 `exit()` 再清取消位），或清理写在正常路径上 |
| 服务偶尔"不可用" | 注册晚于调用方启动；`requires` 拓扑序未实现，现在只能保证清单顺序 |
| `fw_app_state_of()` 查到不相干的 App | 用 `svc_id` 去查 `app_id` 表了，先 `fw_svc_owner()` |
| 加了机制后 App 侧编不过 | 你在 `framework/include/` 里暴露了 RTOS 类型；公开头只出现 `cm_*` 与 `pf_*` |
| 测试全绿但设备上偶发卡死 | 覆盖不到的地方就是这里。补 host 可测的等价物，或写明"只能真机验证" |

## 12. 内存与内联（你既是执法者也是被约束者）

规则原文在 `docs/coding-style.md` §9。框架层多两件事：

1. **`fw_alloc` / `fw_free` 是你实现的**：分配必须登记进 `res_track`、必须能在 `exit()` 阶段被回收、必须能因配额超限而拒绝。**框架自己也不许直接 `malloc`**——你要回收别人的，就不能绕过自己的账本。
2. **静态内存在这层最常见也最危险**：静态表、静态计数器是常驻的，初始化顺序、多任务并发、重启后是否清零，都得写下来。判断标准是"它必须活到多久"——只活一次调用就是栈变量，活到 App 结束就该走 `fw_alloc`。
3. **内联 ≤ 5 行。** 框架头文件里最容易出现"顺手包一层"的 `static inline`，超了就删。
4. **要内存就得先评审**：清单里单列一行（申请什么 / 多大 / 谁释放 / 什么时候释放 / 失败怎么办）。框架层漏写这一行，泄漏会变成"谁都不敢删的全局变量"。
5. **由人拍板。** 配额、静态表规模、缓冲策略不是实现细节，是设计决定。
