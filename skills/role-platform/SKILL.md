# 角色 C · 平台层（tag 4 / `platform`）

你的活只有一句话：**把"一块具体的板子"翻译成框架认识的那张函数指针表。**

框架不认识引脚、不认识 I2C 地址、不认识面板时序。它只认识 `pf_ops_t` 与 `pf_rtos_t` 里的函数指针。你的整个工作就是让这两张表在这块板上为真。

> **所有平台实现共用 tag 4。** 虚拟平台（`host-fake`）与所有真实板一样，不按板再拆 tag。好处是加一块板只需人在 `role 4` 行尾加一个前缀；代价是**板与板之间没有权限隔离，只有目录约定**——这个交换是刻意的，加板成本必须低。

> 权威事实：平台契约以 `platform/port/pf_ops.h` 与 `pf_rtos.h` 两个头为准（**这两个头目前还不存在**）；权限以 `policy.txt` 为准；设计以 `docs/` 定稿文档为准。

## 动手前的两道门（先读这一节，再碰文件）

**第一道：先交清单，等批准，再动文件。**

触发它的是这几类改动：**写 `.c` / `.h` / 构建文件 / 测试文件**，改 `policy.txt`，改头文件里的公开签名，改**已定稿**的文档。纯文档错字、`.txt` 缺口清单不需要门。

清单四项：

1. **要新建 / 要改的文件**：写完整路径，不写"相关文件"这种话。
2. **每处属于哪个 tag**：全仓库平台实现共用 tag 4，所以"你有权写"的判据是**路径在不在 `platform/` 与 `tests/platform/` 下**，而不是"是不是我这块板"。
3. **为什么不能只改现有的。**
4. **大概多少行。**

清单里出现一条你写不了的路径 → 停，报告。**尤其注意**：想改 `platform/port/pf_ops.h` 或别块板的目录，都是越层——那是接口层与另一块板的地盘。

**清单发出后必须停下来，等一句明确答复。**

- **任务描述不是批准。**"实现 X""把这块板接进来"只说明**要做什么**，不说明**可以动手**。
- 唯一算数的是 **"可以""批准""开工"**。没有这句话，不建文件、不写桩、不"先搭个骨架"。
- **不许自我豁免**："我判断这属于已批准范围""前面说过要改所以算批准""这是个小改""我先写完再交清单"——这些话的唯一用途是绕过这一节。
- **不需要门**的只有：只读调查、跑命令看现象、回答问题、写清单本身。
- 清单一次给全（完整路径 / tag / 要动什么 / 怎么验收 / 多少行），末尾直接问"可以吗"；**一份清单覆盖整个任务**，中途要加文件单独问。清单只列必需项，可选项单独一行问。

开干之后仍要守的边界：**改 `pf_ops_t` / `pf_rtos_t` 的签名就停**（那是平台契约，属接口层）；**改 `framework/` 或 `api/` 也停**（读得到 ≠ 写得到）。

批准前不动手，**包括"顺手"的小改**——一次没报备的格式化，review 就分不清哪几行是有意的。

**第二道：只有用户要求"出设计方案"时，才写方案文档。**

不要因为"接一块新板看起来是大事"就自动写文档——**没被要求写的就是噪音**，先把表填起来通常比写方案有用。

- **用户点名要方案 → 先提交申请**：一句话说清"打算写到 `docs/platform/<板名>-<主题>.md`、覆盖哪几个改动、六节各写什么"，**得到同意后才落盘**；写完把路径和要点交回用户审批。方案本身也受管，改它同样走清单 + diff。
- **用户没提方案 → 不写文档。** 改动大就在清单里就地补两行：失败模式是什么、怎么验。

文件名 `docs/platform/<板名>-<一句话主题>.md`（例：`metalio_eink_4_plus-局刷时序.md`）。**板名要写进去**：板与板之间没有权限隔离，文件名是唯一能看出"这块归谁"的地方。六节：

| 节 | 回答什么 |
|---|---|
| 目标 | 改完能做到什么，一句能验证的话 |
| 不改什么 | 明确划出这次不碰的范围 |
| 改动清单 | 文件 + 位置 + 属于哪个 tag |
| 失败模式 | 做错时的症状（花屏 / 偶发卡死 / 只是功耗高）——没有这节，出问题你会先怀疑别处 |
| 怎么验 | 一致性套件里哪一项、或真机上的哪个观测现象 |
| 未决问题 | 还没定的，别在心里留假设 |

方案批准后才写代码。**方案本身也受管**：改它同样走清单 + diff。

## 3. 两份契约，别搞混

| | `pf_ops_t` | `pf_rtos_t` |
|---|---|---|
| 是什么 | 这块板**有什么**（存储、日志、时钟…） | 这块板**怎么并发**（任务、延时、互斥量、信号量、队列） |
| 成员数 | 九项 + `.version` 首字段 | 18 个函数指针 |
| 表达"没有" | 函数指针填 **NULL** | 函数指针填 **NULL** |
| 谁校验 | `fw_init()` 校验 `.version` 与硬必需项，不合规 → `CM_ERR_NOT_SUPPORTED`，**不启动** | 同上 |
| 一致性套件 | `tests/port/` **验它** | **不验它**（只能真机或代码评审） |

**没有 stub 函数。** 早期设计允许"返回 `CM_ERR_NOT_SUPPORTED` 的空实现"，已否决：`static inline` stub 在每个 TU 有独立副本，跨 TU 比较函数指针恒不等，能力自检形同虚设；而且 stub 制造"看起来实现了"的假象。**NULL 就是 NULL。**

## 4. 九项硬必需 + 一个必填字段

漏一项，`fw_init()` 直接拒绝启动。

| # | 签名要点 | 常见错 |
|---|---|---|
| — | `.version = PLAT_PORT_VERSION` | **漏填 = 0**，第一条检查就失败。它不是九项之一，是表的首字段 |
| 1 | `mem_alloc(size, align)` / `mem_free` | 对齐参数被忽略 |
| 2 | `clock_ms()` | 用系统秒级时间冒充毫秒 |
| 3 | `sleep_ms(ms)` | 忙等（功耗高，且会拖住低优先级任务） |
| 4 | `mutex_create` / `mutex_take` / `mutex_give` | 见 §4.1，这是最容易写错的一项 |
| 5 | `task_create` / `task_exit_current` | `task_exit_current` 必须**不返回** |
| 6 | `log_write`（可选） | 没接串口时填 NULL，日志静默丢弃 |

### 4.1 `mutex_take` 的超时语义

时钟是 32 位、单调、可回绕（49.7 天）。**`timeout_ms` 是相对量，不是绝对截止时刻。**

- 自己算 `now + timeout_ms`，比较时用无符号差值：`(int32_t)(now - deadline) < 0`
- `#define PLAT_MUTEX_FOREVER (0xFFFFFFFFu)` 表示永久等待
- 传 `0` 必须是"试一次就返回 `CM_ERR_TIMEOUT`"，**不能**变成永久等待

这三条（相对量 / 回绕安全 / 0 与 FOREVER 的区别）如果每块板各写各的，症状是"设备跑了两天后偶尔卡死"——几乎无法复现，也几乎无法定位到这一行。

## 5. 移植顺序（按这个顺序验收，否则一次冒三个错）

**第 0 步：一致性套件在 host 上跑绿。** 先把板子的实现用 `host-fake` 的编译方式在 PC 上编出来，跑 `tests/port/` 的套件。它验的是"这九项的语义对不对"，不是"这块板能不能工作"——但那已经能砍掉一大半低级错（对齐、不重叠、真的还回去、`mutex_take(m,0)` 立即超时、`sleep_ms` 真让出 CPU、`task_exit_current` 真的不返回）。

1. **整机能启动**：`app_main()` → 平台初始化 → `fw_init()` → `fw_boot()` → 管理器（id 1）把其它 App 拉起来。
2. **`pf_rtos_t` 的 18 个函数**逐项过一遍（套件不覆盖它）。
3. **各项能力**按"先读后写、先软后硬"验：存储 → 网络 → 输入 → 显示。
4. **最后**才谈性能。

## 6. 能力缺失要说清楚，不要假装

| 情况 | 怎么做 | 上层会看到 |
|---|---|---|
| 板上就没有这个器件 | `pf_ops_t` 对应项填 NULL | `CM_ERR_NOT_SUPPORTED`，App 隐藏入口 |
| 器件有，但这块板没接 | 同上 | 同上 |
| 器件有、接了，但你还没实现 | **也填 NULL**，并在 `docs/platform/` 写清"未实现" | 同上——**不要**返回 `CM_ERR_OK` 假装成功 |
| 实现了但这块板有问题（如校验失败） | 返回 `CM_ERR_UNAVAILABLE` 或更具体的错 | `CM_ERR_UNAVAILABLE`，App 显示"暂不可用" |

**能力位与实现是两件事。** `caps()` 回答"有没有这块硬件"，不回答"接口发布了没有"：v1 不发布 `disp.h`，但 `PF_CAP_DISPLAY` 照样可以是 1。未定义的位必须读出 0——把没定义的位设成 1 也算缺陷。

## 7. 平台目录里放什么

```
platform/<板>/
├─ pf_ops_impl.c       g_pf_ops 实例（九项 + .version）
├─ pf_rtos_impl.c      g_pf_rtos 实例（18 个函数指针）
├─ board_init.c        总线 → 器件 → 中断的初始化顺序
├─ board.h / board.c   引脚、地址、时序参数（**差异是数据，不是条件编译**）
└─ panel_xxx.c         只属于这块板的器件驱动
```

公共驱动放 `platform/drivers/`（**归接口层，不是你的写区**）：多平台共用的器件驱动写一份，板级目录只负责注入引脚/地址/时序参数，驱动不写死引脚和地址。差异是数据，不是 `#ifdef`。

**没有模板可抄。** 本仓库取消了 `platform/template/`。工程里会有墨水屏例程，实现时**参考它、按契约自主写**——不是把一个现成工程拷进来改引脚宏，那是"看起来能跑"，不是"接了进来"。

---

## 8. 三条禁令

1. 公共驱动与 `platform/<板>/` **不得 include `api/af_api/` 或 `framework/`**。
2. **框架不依赖任何具体驱动或板**：删掉所有板级目录，框架仍应能编译、能链 `host-fake` 跑通单测。
3. 板级目录里不得出现对 App 的引用，也不得知道"这一页该不该重刷"——策略不是平台的事。

> 这三条把"仓库里有一堆硬件代码"和"框架不针对硬件"分开了：硬件代码是**可选资产**，框架的编译与测试**不经过它们**。

## 9. 自检与交付

```bash
python tests/test.py port        # 一致性套件（同一份文件，host 与真机各跑一次）
python tests/test.py platform    # 板级实现的 host 侧测试
python tools/validate.py --as 4  # 全部门禁 + 写入判定
```

`tests/port/pf_conformance.c` 还没写（它要 `platform/port/pf_ops.h`，那个头也还没有）——所以这两条现在会 `SKIP`，**`SKIP` 不是通过**。板级差异不靠命令行换目录：同一份套件，把你这块板的 `pf_ops_t` 编进来即可。

**测试分工要分清，别越界：**

| 测试 | 谁写 | 你干什么 |
|---|---|---|
| `tests/port/pf_conformance.c` | 接口层（tag 5） | **只跑**。发现它验的东西不对 → 报告，不要改它（改它等于改验收标准） |
| `tests/platform/<板>/test_*.c` | **你**（tag 4） | 板级实现里 host 能测的部分：配置表自洽、降级路径、`caps()` 与实际实现一致 |
| `tests/support/` 夹具 | 接口层 | 用；缺了就报告 |

写板级测试时同样只打印 `PASS/FAIL/SKIP/SUMMARY` 四种行、用 `tinytest.h` 的 `TT_CASE`/`TT_PROGRAM`/`TT_RUN`、**不要链接 `platform/host-fake/`**（它是参考实现，不是裁判）。完整规则见 `docs/test-plan.md`。

**主反馈回路是一致性套件，不是"烧进去看看"。** 九项契约的错误恰恰都是"烧进去也看不出来"那类——相对超时写成绝对截止 → 跑两天偶发卡死；`sleep_ms` 忙等 → 只是功耗高一点。

套件查得到：`.version`、`mem_alloc/free` 对齐与真的释放、`clock_ms` 单调、`sleep_ms` 是否让出、`mutex_take(m,0)` 立即超时、`mutex_take(m,20)` 耗时区间、`PLAT_MUTEX_FOREVER`、`mutex_give` 未持有、`task_create` 真被执行、`task_exit_current` 不返回。

套件查不到：32 位回绕（逻辑在 `mutex_take` 内部）、ISR 安全、栈深、优先级——**只能真机验或代码评审**，别把"套件全绿"当"这块板能工作"。

`tests/port/pf_conformance.c` 与 `platform/port/pf_ops.h` 现在都还没有，所以 `port` 那一层会 `SKIP`——**`SKIP` 不是通过**：交付时写清跳过的是哪一步、为什么，或者老实写 `NOT RUN`。

**注释**：`pf_ops_impl.c` 里你实现的每一项都要有中文注释，写清"为什么这样填"（尤其是返回 `CM_ERR_NOT_SUPPORTED` 的那几项）；板级全局/静态变量（`static uint8_t buf[8192]` 这种）必须有注释说明用途、大小由来、谁释放。函数注释块四项不缺——入参、返回值、**线程与中断可用性**（哪些项在 ISR 里会被调用，直接写出来）、注意事项。规则见 `docs/coding-style.md` §10。

交付 = 四行状态 + 一份清单，缺一段视为没交付：

```
Build:        PASS / FAIL / NOT RUN
Host tests:   PASS / FAIL / NOT RUN（贴数字）
Device tests: PASS / FAIL / NOT RUN（没做就写 NOT RUN）
Unverified:   还有什么没验证、为什么
```

清单四段（标题固定，别改）：

- **完成了什么**：逐条对应你提的要求 → 改了哪些文件。
- **没完成什么**：每条写原因、卡在哪（缺头文件？缺授权？）。
- **需要你处理什么**：只有人能做的事——删文件、改 `policy.txt`、授权烧录、拍板方案。
- **其他说明**：顺手发现的不一致、我不确定的地方、验证的边界。

**不得把"host 套件全绿"说成"真机验证通过"。** 本仓库在 host 上验的是语义，不是时序。

## 10. 常见错误

| 症状 | 真实原因 |
|---|---|
| `fw_init()` 直接失败，什么日志都没有 | `.version` 漏填（= 0）或某个硬必需项是 NULL |
| 设备跑两天后偶发卡死 | `mutex_take` 把相对超时当绝对截止，或没处理 32 位回绕 |
| 功耗偏高但功能正常 | `sleep_ms` 是忙等 |
| App 里"没有这能力"的判断总是不生效 | 该能力项填了 stub 而没填 NULL（或反过来） |
| 改了框架才能支持这块板 | 抽象位置错了：差异应该是数据（配置结构体），不是框架里的分支 |
| 一致性套件全绿但真机上出问题 | 套件不覆盖 `pf_rtos`、ISR 安全、栈深、优先级 |
| 想让接口层给某个器件加个专用函数 | 那是能力契约变更，提提案；不要在自己目录里 `#define` 绕过 |

## 11. 内存与内联（平台层最容易绕过这条）

规则原文在 `docs/coding-style.md` §9。平台层有三处特殊：

1. **"我在平台层"不是例外。** 除了 `pf_ops_t` 的内存项本身就是"内存从哪来"的背面（属被评审过的既定设计），**平台层的其他代码同样只能走 `fw_` 层**。不要自己 `malloc` 一个 DMA 缓冲然后当能力交上去——框架看不见它，也就回收不了它。
2. **DMA / 外设缓冲是这条规则的老窝。** 常见写法是 `static uint8_t buf[8192];` 一放了事。要么写明"它必须常驻、由谁重置、并发谁负责"，要么改成 `fw_alloc`。**静态大数组是最容易被 review 漏掉的一种申请。**
3. **内联 ≤ 5 行。** 寄存器操作的包装函数很容易超标，超标就写普通函数。
4. **要内存就得先评审**：申请什么 / 多大 / 谁释放 / 什么时候释放 / 失败怎么办（平台侧尤其要写"分配失败时驱动怎么退"）。
5. **由人拍板。** 缓冲大小、是否常驻、用不用 DMA 的固定区域，都是设计决定，不是移植细节。
